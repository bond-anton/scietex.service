# Architecture Review

- **Date:** 2026-09-09
- **Version:** v4.0.0 (`src/scietex/service/version.py`)
- **Scope:** entire repository — `src/scietex/service/`, `tests/`, `examples/`
- **Method:** read all `docs/architecture/*` as an initial map (not authoritative), verified claims against source, read every source file end-to-end, ran targeted reproductions of suspected defects.
- **Type:** deep architectural review (read-only). The only repository change is this document.

---

## Executive Summary

The architecture is **fundamentally sound**. The three-level hierarchy
(`BasicWorker` → `TaskProcessor` → `ValkeyWorker`), the clean feature→core
dependency direction, the narrow `TaskHandlerContext` handler boundary, the
at-least-once transport model, and the config-object refactor (AR-046) are all
genuine, well-preserved design decisions. The prior review (2026-09-08,
AR-041..AR-055) has been largely and correctly resolved.

This review surfaced one **critical, reproducible defect** plus a cluster of
systemic medium-grade weaknesses in the manager/lifecycle/concurrency
subsystem. The critical defect is an **import-time crash in the package's own
graceful-degradation path**: the in-package subpackage `scietex.service.logging`
shadows the stdlib `logging` module inside the package namespace, so the
`VALKEY_AVAILABLE` fallback (`__init__.py`'s `except ImportError` branch) raises
`AttributeError` exactly when `valkey-glide` is missing — the one scenario the
guard exists to handle. Reproduced by importing the package with `glide`
un-importable.

The strongest recurring theme is **weak observability and ownership in the
manager subsystem**: the `ManagerStatus` state machine never enters `RUNNING`,
a manager that exhausts its retry budget dies silently while the worker reports
`RUNNING`, task timeouts run on wall-clock time, and a single shared
`GlideClient` is torn down by one component while others use it. None of these
break the happy path today, but they are exactly the class of problem that
degrades a daemon into "running but not working."

**What to fix first:** AR-056 (the import crash) is resolved — the in-package
`logging` subpackage was renamed to `log_handlers` (commit `64daf94`), restoring
the advertised core-only install. AR-057 (manager `RUNNING` status) is also
resolved — `run_manager` now records `RUNNING` and `start_manager`'s guard is
status-aware. AR-058 (monotonic timeout clock), AR-059 (serialized connection
ownership), AR-061 (self-managed logging-handler connection), and AR-062
(configurable task-level timing constants) are resolved
(2026-09-09). AR-063 (manager death signaling) is also resolved (2026-09-09):
a give-up manager now ends in terminal `FAILED`, surfaced via
`ManagerRuntime.failed_managers`/`BasicWorker.failed_managers` and a CRITICAL
watchdog log. The remaining moderate issue, AR-060 (XAUTOCLAIM lease), is a
scale-out hardening task rather than a quick observability fix.

## Architecture Assessment

### Boundaries
Module boundaries are well chosen and mostly respected. Core (`basic_worker`,
`task_processor`, `task_handler`, `manager`, `logging`, `config`, `utils`) never
imports `valkey`; `ValkeyWorker` extends `TaskProcessor` (feature → core).
`task_handler` receives a narrow frozen context and holds no reference to the
worker. The one boundary that leaks is **logging**: the generic
`LoggingLifecycle` and the transport-specific `ValkeyWorker` *both* drive the
same handler lifecycle, and `ValkeyWorker` reaches into the external
`scietex.logging.AsyncValkeyHandler` internals (`.client`,
`logging_running_event`) rather than staying on its public interface
(AR-061, resolved — the handler now owns its own connection via `valkey_config=`
and the worker no longer touches `.client`).

### Responsibilities
Responsibility extraction (AR-003) is good: `BasicWorker` keeps identity,
state machine, and hooks; `ManagerRuntime` owns manager bookkeeping;
`LoggingLifecycle` owns handler bookkeeping. Residual leakage: `ValkeyWorker`
owns connection *teardown* of a client it shares with several concurrent
components (AR-059, resolved — connect/disconnect are lock-serialized and the
logging handler runs on its own connection), and the transport wire format is
inseparable from the handler contract (AR-064).

### Dependencies
Direction is correct everywhere except one **intra-package circular import**
pair: `manager/__init__.py` re-exports `ManagerRuntime` from `runtime.py`, which
imports `Manager`/`ManagerStatus` back from `__init__.py` (identical pattern in
`logging/`). The re-exports are unused and the cycle is gratuitous (AR-065).

### Abstractions
`TaskHandler`/`TaskHandlerContext` and the config structs are deep, well-shaped
abstractions. The `@Manager` class-decorator + MRO `__dict__` reflection is a
clever implicit-registration mechanism, but it is stringly-named and fragile to
method renames (AR-068). The `Manager` decorator also carries a `cleanup`
parameter that was previously unexercised; it is now covered by a test and an
example (AR-067 resolved — keep+test, not removal).

### Lifecycle
The worker state machine (STOPPED→STARTING→RUNNING→STOPPING→STOPPED) is
consistent, guarded, and tested. The **manager** state machine is now recorded
(`ManagerStatus.RUNNING` is set when the loop starts, AR-057 resolved), and a
manager that gives up now ends in terminal `FAILED` surfaced through
`failed_managers` and a CRITICAL watchdog log instead of silently vanishing
while the worker stays `RUNNING` (AR-063 resolved).
Construction-time filesystem writes violate the "constructible anywhere"
promise (AR-066).

### Concurrency
Cancellation, watchdog, and requeue semantics are carefully worked out
(asyncio.wait vs wait_for, ack-after-stop). The shared-client teardown across
concurrent tasks is now serialized behind an `asyncio.Lock` and intake reconnects
only on glide errors (AR-059 resolved).
(Timeout enforcement now uses `time.monotonic()`, AR-058 resolved.)

### State ownership
`GlideClient` is now mutated by a single serialized owner (`connect`/`disconnect`
behind `_client_lock`), and the logging handler owns a separate connection
(AR-059 resolved).
`_task_entry_ids`, `running_tasks`, `task_queue`, handler maps are all correctly
owned by `TaskProcessor`/`ValkeyWorker`. No module-level mutable global state.

### Testability
Good and deterministic, but heavily white-box: tests mutate `worker._client`,
`_task_entry_ids`, `_manager_runtime.tasks`, `_logging_lifecycle.statuses`
(AR-071). This is a trade-off that made the AR-045/046 refactors
test-repointing-heavy.

### Extensibility
Handlers are cleanly pluggable (incl. named instances AR-053 and stateful
`handler_kwargs`). The config structs extend compositionally
(`WorkerConfig` → `TaskProcessorConfig` → `ValkeyWorkerConfig`). The hardcoded,
non-configurable task-level timing constants were promoted into the config
structs (AR-062, resolved). One remaining rough edge is the `_config` re-store
pattern in subclass constructors (AR-069).

## Strengths

1. **Clean feature→core dependency direction.** `ValkeyWorker` is an overlay on
   `TaskProcessor`; core modules never import `valkey`/`glide`. The processor is
   fully usable without Valkey.
2. **Narrow, safe handler contract.** `TaskHandlerContext` (frozen dataclass of
   `service_name`/`instance_id`/`logger`) means a handler cannot reach processor
   internals. The ABC (`supported_tasks` + `handle`) plus first-match `supports`
   dispatch is minimal and clear.
3. **Immutable typed configuration.** `WorkerConfig`/`TaskProcessorConfig`/
   `ValkeyWorkerConfig` (`msgspec.Struct, frozen=True`) with
   `__post_init__` range validation replacing ~15 constructor kwargs. MIN/MAX/
   DEFAULT constants are centralized. `ValkeyWorkerConfig` is correctly kept out
   of the core `config.py` to avoid dragging `glide` into the core.
4. **Correct at-least-once transport.** Enqueue-without-ack, ack+xdel only in
   `on_task_completed` after the handler terminates, `XAUTOCLAIM` recovery, and
   the retry-copy-before-ack ordering (XADD then XACK) are all correctly
   sequenced.
5. **Careful cancellation semantics.** `asyncio.wait` (not `wait_for`) for
   cancellation, requeue only after the handler actually stopped, and
   `_force_stopped()` so a cancelled startup/shutdown never strands a terminal
   state.
6. **Single guarded glide import** (`valkey/_glide.py`, AR-048) and a narrow
   `except ImportError` at the package boundary (AR-019) — the *intent* of the
   graceful-degradation mechanism is right, and its fallback path is now fixed
   (AR-056 resolved: the in-package `logging` subpackage was renamed to
   `log_handlers`).
7. **Bounded, restart-safe manager runtime** with inline retry, consecutive-
   failure budget, and cleanup-in-`finally` (AR-003).

## Critical Issues

### AR-056 — In-package `logging` subpackage shadows stdlib `logging`; the `VALKEY_AVAILABLE` fallback crashes on import

- **Status:** ✅ RESOLVED (2026-09-09)
- **Severity:** CRITICAL
- **Evidence:** `src/scietex/service/__init__.py:20` (`import logging`),
  `__init__.py:69` (`logging.getLogger(__name__).warning(...)` inside the
  `except ImportError` guard); the in-package subpackage
  `src/scietex/service/logging/__init__.py`. Importing the package imports the
  subpackage via `from .basic_worker import BasicWorker` →
  `basic_worker.py:30-31` → `from .logging import ...`.
- **Problem:** `import logging` binds the stdlib `logging` module into the
  package namespace under the key `logging`. Importing the subpackage
  `scietex.service.logging` then overwrites that same namespace key with the
  subpackage module (Python sets `scietex.service.logging` as an attribute of
  the parent package). After `from .basic_worker import BasicWorker`, the name
  `logging` in `__init__.py` refers to the subpackage, which has no
  `getLogger`. The `except ImportError` fallback — the branch that runs *only*
  when `valkey-glide` is absent — therefore raises
  `AttributeError: module 'scietex.service.logging' has no attribute 'getLogger'`
  instead of emitting the intended warning and returning with
  `VALKEY_AVAILABLE=False`.
- **Why it matters:** This is the exact scenario the guard exists for. A user
  who installs the core package (`pip install scietex.service`) and imports it
  gets a crash, not a usable `BasicWorker`/`TaskProcessor` with a warning. It
  defeats the package's advertised "importable without valkey-glide" property.
  It is also a latent namespacing hazard: any future use of the bare name
  `logging` in `__init__.py` will hit the same trap. The bug is invisible in
  normal development because the happy path (glide present) never executes the
  `except` branch.
- **Recommendation:** Stop the stdlib name from being shadowed. Minimal fix:
  reference the stdlib logger without relying on the bare `logging` name in
  `__init__.py` (e.g. `import logging as _logging` and use
  `_logging.getLogger(...)`). Architecturally stronger: rename the in-package
  subpackage so it cannot collide with a ubiquitous stdlib module (e.g.
  `loghandlers`/`logging_lifecycle`), removing the hazard for the whole package.
- **Confidence:** HIGH — reproduced with a simulated missing `glide`; also
  confirmed via `scietex.service.logging is not <stdlib logging>`.
- **Resolution:** Renamed the in-package subpackage `scietex.service/logging/`
  → `scietex.service/log_handlers/` (commit `64daf94`), so it can no longer
  shadow stdlib `logging` in the package namespace. Updated all internal
  references (`basic_worker.py`, tests) and docs. External `scietex.logging`
  imports and stdlib `import logging` untouched. Verified: importing
  `scietex.service` with `glide` blocked now prints `OK False` with no
  `AttributeError`; 115 tests pass.

## Moderate Issues

### AR-057 — Manager lifecycle state machine never enters `RUNNING` (dead enum value, no observability)

- **Status:** ✅ RESOLVED (2026-09-09)
- **Severity:** MEDIUM
- **Evidence:** `manager/__init__.py:14-20` (`ManagerStatus` declares
  `STARTING/RUNNING/STOPPING/STOPPED`); `manager/runtime.py:141`
  (`start_manager` sets `STARTING`), `runtime.py:117/123` (`run_manager`'s
  `finally` sets `STOPPING` then `STOPPED`). A grep for `ManagerStatus.RUNNING`
  finds zero assignments in `src/` or `tests/`.
- **Problem:** The status dict (`ManagerRuntime.statuses`) transitions
  `STARTING → STOPPING → STOPPED` and never records `RUNNING`. The declared
  state machine is a lie: a consumer inspecting `statuses` can never observe a
  manager as running, and `start_manager`'s re-entry guard is `name in
  self.tasks`, not the status, so the enum is effectively decorative.
- **Why it matters:** `statuses` is the only manager-level observability
  surface. A dead `RUNNING` state means any future health/supervision logic
  built on it will be wrong, and it hides the real manager lifecycle (AR-063)
  from operators and tests alike.
- **Recommendation:** Set `statuses[name] = ManagerStatus.RUNNING` when the
  loop actually starts (before the first iteration), and make `start_manager`'s
  guard status-aware rather than task-dict-aware.
- **Confidence:** HIGH.
- **Resolution:** `run_manager` now sets `statuses[name] = ManagerStatus.RUNNING`
  immediately after the `[START]` log and before the retry loop, so the status
  reads `STARTING → RUNNING → STOPPING/STOPPED`; `start_manager`'s re-entry
  guard is now status-aware (`STARTING`/`RUNNING`) instead of task-dict-aware.
  Added `test_manager_status_reports_running_and_stopped`. 116 tests pass.

### AR-058 — Task timeout enforcement uses wall-clock time, inconsistent with monotonic usage elsewhere

- **Status:** ✅ RESOLVED (2026-09-09)
- **Severity:** MEDIUM
- **Evidence:** `task_processor.py:607` (`TaskTracker(..., started=time.time())`)
  and `task_processor.py:669` (`now = time.time()` in `watchdog`). Contrast
  `valkey/worker.py:273/280/283`, which correctly uses `time.monotonic()` for
  heartbeat duration measurement.
- **Problem:** The task-timeout mechanism (the core of `watchdog`) computes
  elapsed time from `time.time()`, the system wall clock. NTP steps, manual
  clock changes, or DST adjustments move this clock; a forward jump can make
  tasks appear to exceed their timeout and be cancelled/requeued spuriously, and
  a backward jump can defer timeouts indefinitely.
- **Why it matters:** This is a correctness property of the timeout/cancellation
  boundary: it must be monotonic. A spurious cancellation is not just cosmetic —
  under `timeout_action="requeue"` it causes the task to be re-executed from
  scratch (duplicate work). The codebase already uses `time.monotonic()` in the
  adjacent heartbeat path, so this is an inconsistency, not an unknown idiom.
- **Recommendation:** Use `time.monotonic()` for `TaskTracker.started` and the
  watchdog's `now`.
- **Confidence:** HIGH.
- **Resolution:** Switched `TaskTracker.started` (`task_processor.py:607`) and the
  watchdog's `now` (`task_processor.py:669`) from `time.time()` to
  `time.monotonic()`, consistent with the heartbeat path. Both timestamps are
  only compared against each other, so the elapsed-time computation is now
  immune to wall-clock jumps. 30 task-processor tests pass.

### AR-059 — Single shared `GlideClient` is torn down by intake reconnect while concurrently used by other components

- **Status:** ✅ RESOLVED (2026-09-09)
- **Severity:** MEDIUM
- **Evidence:** `valkey/worker.py:562` (`fetch_tasks` on read error calls
  `disconnect()` then `connect()`), `worker.py:236-248` (`disconnect` sets
  `_client = None` and closes it), while `heartbeat` (`worker.py:263-279`),
  `_register_instance`/`_unregister_instance` (`worker.py:374-406`), and the
  injected `AsyncValkeyHandler` worker all use `self.client` concurrently in
  separate asyncio tasks.
- **Problem:** One component (intake) is authorized to tear down and recreate
  the shared client mid-flight while three other components hold or use it.
  Because `disconnect()`/`connect()` reassign `self._client` at await
  boundaries, a heartbeat that already read `self.client` can `await
  self.client.set(...)` on a client that `fetch_tasks` just closed, or a
  registry `SADD`/`SREM` can target a stale client. The failures are swallowed
  and logged, so they surface as silent heartbeat/registry gaps rather than
  errors.
- **Why it matters:** This is an ownership-of-shared-resource problem: the
  client has one nominal owner but four concurrent users, and one of them can
  invalidate it under the others. As asyncio scheduling interleaves, the
  failure modes are timing-dependent and hard to reproduce. It will bite under
  flaky network conditions (the very conditions reconnect exists for).
- **Recommendation:** Make connection lifecycle a single serialized owner (e.g.
  a dedicated connection/transport component that performs connect/disconnect
  and publishes a client handle), or introduce a generation/versioned client
  handle so concurrent users detect staleness before issuing a command, rather
  than letting intake reassign `self._client` while others are mid-command.
- **Confidence:** MEDIUM — asyncio cooperativeness bounds the window (no
  preemption between synchronous statements), but the interleaving is real and
  the guarded-and-use sequences for registry/heartbeat do span await points.
- **Resolution:** Serialized the operational client's `connect()`/`disconnect()`
  behind an `asyncio.Lock` (`worker.py:163`) via `_connect_locked`/
  `_disconnect_locked` helpers, so only one task mutates `_client` at a time,
  and narrowed `fetch_tasks`' reconnect trigger to glide errors only
  (`GlideConnectionError`/`RequestError`/`GlideTimeoutError`) so genuine
  non-glide bugs propagate instead of reconnecting. The logging handler was
  decoupled onto its own connection (see AR-061). Added tests for concurrent
  connect serialization and glide-only reconnect; 121 tests pass.

### AR-060 — `XAUTOCLAIM` pending-recovery can reclaim in-flight entries (no per-entry lease)

- **Severity:** MEDIUM
- **Evidence:** `valkey/worker.py:41` (`DEFAULT_CLAIM_MIN_IDLE_MS = 1000`),
  `worker.py:448-452` (`xautoclaim(..., DEFAULT_CLAIM_MIN_IDLE_MS, ...)`), and
  the recovery trigger on first `fetch_tasks` (`worker.py:518-524`).
- **Problem:** The only signal separating "abandoned" from "being processed" is
  the pending-entry idle time, and the floor is 1 s — far below the execution
  time of any non-trivial handler. A handler that legitimately runs for
  seconds-to-minutes leaves its stream entry idle for that whole duration; a
  second replica starting up (or the same worker after a quick restart) will
  `XAUTOCLAIM` and re-enqueue that entry, causing duplicate processing. There is
  no lease renewal or per-entry heartbeat while a handler works, so the claim
  floor is the *only* guard.
- **Why it matters:** Duplicate processing is a correctness failure in the
  scale-out model this library exists to support ("distributed task queues").
  The prior fix (raising the floor from 0 to 1000 ms) only narrows the window;
  it does not eliminate the fundamental race, because the bound is on idle time
  rather than on handler liveness. Raising the floor further trades recovery
  latency against safety, and 1 s is almost certainly below any realistic
  handler duration.
- **Recommendation:** Introduce a real liveness signal for in-flight entries
  (e.g. refresh the entry's idle time / re-claim to self, or track in-flight
  entry ids in a shared, TTL-backed registry that recovery consults), or raise
  the claim floor to a configurable value derived from `max handler duration`
  rather than a fixed 1 s. At minimum, document the duplicate-processing
  exposure explicitly.
- **Confidence:** MEDIUM (behavior), HIGH that the 1 s floor is far below
  typical handler duration.

### AR-061 — Logging-handler lifecycle is split across two owners; the worker reaches into external handler internals

- **Status:** ✅ RESOLVED (2026-09-09)
- **Severity:** MEDIUM
- **Evidence:** `LoggingLifecycle.start_handlers`/`shut_down_handlers`
  (`logging/lifecycle.py:62/104`) are the generic owner, but the Valkey handler
  is (a) constructed lazily in `ValkeyWorker.connect` (`worker.py:222`) after
  `start_handlers` has already run, (b) started manually in `connect`
  (`worker.py:223-224`, checking `handler.logging_running_event.is_set()` then
  `handler.start_logging()`), and (c) stopped twice — in `cleanup`
  (`worker.py:360-361`, `stop_logging()`) and again in `_shutdown` via
  `LoggingLifecycle.shut_down_handlers`. The worker mutates
  `handler.client` (`worker.py:188/245`) and reads `logging_running_event`
  (`worker.py:223`), both implementation details of the external
  `scietex.logging` package.
- **Problem:** The generic handler lifecycle and the transport-specific handler
  lifecycle are two code paths that can start/stop the *same* handler, with a
  guard (`logging_running_event`) papering over the double-start. The worker's
  coupling to `AsyncValkeyHandler`/`AsyncBrokerHandler` internals goes beyond
  the public `start_logging`/`stop_logging` interface, so the library breaks if
  the external package changes those attributes.
- **Why it matters:** Duplicated responsibility (two owners of one resource),
  ordering fragility (the Valkey handler is not yet registered when
  `start_handlers` first runs, so the generic path can't manage it on the first
  cycle), and a cross-package abstraction leak. The unused `name` parameter in
  `register_logger_handler` (AR-070) is a symptom of this half-finished
  extraction.
- **Recommendation:** Construct and register *all* handlers (including the
  Valkey one) before `start_handlers` runs, so `LoggingLifecycle` is the single
  lifecycle owner and `connect()` only injects the client. Route client
  injection through a narrow, public seam rather than poking handler attributes.
- **Confidence:** HIGH.
- **Resolution:** `AsyncValkeyHandler` is now constructed once with
  `valkey_config=` (a scalar dict translated from the typed `ValkeyConfig`) so
  it owns, closes, and reconnects its own `GlideClient` autonomously; the worker
  no longer injects or re-points `handler.client`, and `disconnect()` no longer
  nulls it. Only the raw-`GlideClientConfiguration` fallback keeps `client=`
  injection. The worker still starts/stops the handler via the public
  `start_logging()`/`stop_logging()` seam. Tests updated; 121 tests pass.

### AR-062 — Task-level timing constants are hardcoded module constants, not configurable

- **Status:** ✅ RESOLVED (2026-09-09)
- **Severity:** MEDIUM
- **Evidence:** `task_processor.py:30/33/35` (`DEFAULT_TASK_TIMEOUT = 3`,
  `TASK_QUEUE_FETCH_TIMEOUT = 1`, `WORKER_TASK_CANCELLATION_TIMEOUT = 5`) and
  `valkey/worker.py:41` (`DEFAULT_CLAIM_MIN_IDLE_MS = 1000`). All worker/
  processor timings and retry bounds were centralized into `config.py` (AR-046),
  but these four remain module-level and are unreachable from any config struct.
- **Problem:** `DEFAULT_TASK_TIMEOUT` is a real operational knob — it is the
  per-task cancellation deadline when `TaskTimeout.timeout is None`
  (`task_processor.py:671-673`) — yet a user cannot tune it globally and must
  set it on every `TaskData`. `WORKER_TASK_CANCELLATION_TIMEOUT` (how long
  shutdown/watchdog wait for a cancellation-ignoring handler) is equally
  untunable. The config extraction is therefore incomplete and inconsistent:
  some timeouts are configurable, others are magic numbers.
- **Why it matters:** A hardcoded 3 s default task timeout is likely wrong for
  real workloads and cannot be corrected without code changes; the inconsistency
  also signals to future contributors that some constants belong in `config.py`
  and others do not, without a stated rule.
- **Recommendation:** Promote these four constants into the appropriate config
  structs (`TaskProcessorConfig` for the first three; `ValkeyWorkerConfig` or
  `ValkeyConfig` for the claim floor) with the same MIN/MAX/DEFAULT treatment,
  keeping `TaskTimeout.timeout=None` as the per-task "use the configured default"
  sentinel.
- **Confidence:** HIGH.
- **Resolution:** Promoted the four constants into the config structs with the
  AR-046 MIN/MAX/DEFAULT + `None`-means-default treatment. `TaskProcessorConfig`
  gained `task_timeout` (default 3, bounds `[0.1, 3600]`, with `<= 0` preserved
  as the "no timeout" sentinel so the watchdog's unbounded escape hatch is
  retained), `task_queue_fetch_timeout` (default 1, `[0.01, 60]`), and
  `task_cancellation_timeout` (default 5, `[0.1, 60]`); `ValkeyWorkerConfig`
  gained `claim_min_idle_ms` (default 1000, `[1, 3600000]`). Each resolves once
  in the worker `__init__` to a private attribute (read in the hot loops), and
  the module-level constants were removed from `task_processor.py`/
  `valkey/worker.py`. `TaskTimeout.timeout=None` remains the per-task "use the
  configured default" sentinel.

### AR-063 — A manager that exhausts its retry budget dies silently; the worker keeps reporting `RUNNING`

- **Status:** ✅ RESOLVED (2026-09-09)
- **Severity:** MEDIUM
- **Evidence:** `manager/runtime.py:94-101` (`if consecutive_failures >
  manager_max_retries: ... break`), `runtime.py:116-128` (`finally` marks
  STOPPED and removes the task from `self.tasks`). The worker state is
  unchanged (`BasicWorker` never inspects `ManagerRuntime.statuses`/`errors`
  after startup).
- **Problem:** After `manager_max_retries + 1` consecutive failures a manager
  stops permanently and is removed from tracking, but the worker stays `RUNNING`
  and nothing observes the death. If the `TaskManager` or `TaskQueueManager`
  ever hit this (currently unlikely because the built-ins swallow their own
  errors, but trivially reachable by a custom `@Manager`), the worker is
  "running but not working" — the worst failure mode for a daemon.
- **Why it matters:** There is no supervisor, no aggregate health, no error
  propagation from `ManagerRuntime.errors` to the worker, and (per AR-057) no
  way to even see that a manager ever ran. A permanently-failing manager is
  invisible to operators and to any external liveness probe keyed on worker
  `state`.
- **Recommendation:** Surface manager death to the worker (e.g. an aggregate
  health/error accessor or an event) and make the degradation observable, or
  fail the worker when a critical manager gives up. At minimum, expose
  `ManagerRuntime.errors`/`statuses` through a documented read-only property.
- **Confidence:** HIGH (behavior), MEDIUM (severity — depends on how much custom
  managers are trusted to be robust).
- **Resolution:** Added a terminal `ManagerStatus.FAILED` value
  (`manager/__init__.py`) that a give-up manager lands in instead of `STOPPED`
  (`run_manager` sets a `gave_up` flag on retry-budget exhaustion and the
  `finally` override ends the manager in `FAILED`); clean shutdown still ends in
  `STOPPED`. Added a read-only `ManagerRuntime.failed_managers` accessor and a
  delegating `BasicWorker.failed_managers` property, and the watchdog now logs
  a CRITICAL message naming any failed managers each tick (no auto-shutdown,
  per the approved observe+log design). Tests: an always-failing manager ends
  `FAILED` and appears in `failed_managers`; a cleanly-stopped manager stays
  `STOPPED`. 141 tests pass.

## Minor Issues

### AR-064 — `TaskData` doubles as the durable wire format; handler contract and transport envelope are not separable

- **Severity:** LOW
- **Evidence:** `task_handler/schemas.py:30-45` (`TaskData`), msgpack-encoded
  directly as the stream entry value in `valkey/worker.py:423-425`
  (`return_task_to_queue`) and decoded in `worker.py:544`
  (`msgspec.msgpack.decode(payload, type=TaskData)`).
- **Problem:** The in-process dispatch contract and the on-the-wire format are
  the same struct. There is no envelope, no version field, and no distinction
  between "what the handler sees" and "what the transport persists." Any change
  to `TaskData` for handler ergonomics is wire-breaking, and the wire format
  constrains the handler contract.
- **Why it matters:** This is the classic "schema-as-wire-format" coupling. It
  is acceptable for a single-transport v1, but it removes any migration path
  for the durable queue (no versioning) and couples two concerns that will
  plausibly evolve at different rates.
- **Recommendation:** Introduce a thin transport envelope (with a format
  version) that carries the serialized `TaskData`, so the wire format can
  evolve independently of the handler contract.
- **Confidence:** MEDIUM (it is a defensible simplicity trade-off today, but a
  likely future problem).

### AR-065 — Gratuitous intra-package circular imports via unused re-exports

- **Severity:** LOW
- **Evidence:** `manager/__init__.py:95` (`from .runtime import ManagerRuntime`)
  with `manager/runtime.py:12` (`from . import Manager, ManagerStatus`);
  `logging/__init__.py:64` (`from .lifecycle import LoggingLifecycle`) with
  `logging/lifecycle.py:12` (`from . import LoggerStatus`). The re-exports are
  unused: `basic_worker.py:31/33` imports `ManagerRuntime`/`LoggingLifecycle`
  from their submodules directly, and no `src/`, `tests/`, or `examples/` code
  imports them from the package root.
- **Problem:** Two `__init__ ↔ submodule` circular-import pairs exist purely to
  re-export symbols nothing consumes from the root. They resolve only because
  of import ordering (the `Manager`/`LoggerStatus` names are defined before the
  bottom-of-file re-import), which is fragile to future reordering.
- **Why it matters:** It contradicts the "no circular dependencies" claim in
  the architecture map (which only considered cross-package cycles), and it
  couples module initialization order in a way that is easy to break.
- **Recommendation:** Drop the two re-exports from `manager/__init__.py` and
  `logging/__init__.py` (keep `Manager`/`ManagerStatus`/`LoggerStatus`/
  `parse_logging_level` where they are), eliminating the cycles.
- **Confidence:** HIGH.

### AR-066 — Construction-time filesystem side effects in `ValkeyWorker.__init__`

- **Severity:** LOW
- **Evidence:** `valkey/worker.py:111` (`read_valkey_config(self.conf_dir)` with
  the default `create_default=True`), which writes `valkey.yml`
  (`valkey/config.py:303-305`) and can `mkdir` the config dir
  (`valkey/config.py:291`); `utils/config.py:73` (`prepare_conf_dir` creates
  `~/.config/scietex`).
- **Problem:** Constructing a `ValkeyWorker()` with no explicit config mutates
  the filesystem (writes a default `valkey.yml`, creates directories) before
  `start()` is ever called, and `read_valkey_config` can raise `RuntimeError`
  at construction for a corrupt/invalid config file. This contradicts the
  architecture's "a worker can be constructed anywhere" property, which was
  specifically established for `BasicWorker` by removing loop access from
  `__init__` (AR-015).
- **Why it matters:** `__init__` is not side-effect-free; read-only/container
  environments and config-inspection tooling get writes and exceptions at an
  unexpected time. AR-047 added `create_default=False`, but the worker's own
  bootstrap path still uses the write path.
- **Recommendation:** Defer config loading/default-creation to
  `initialize()`/`start()` (or accept a pre-built `ValkeyConfig`/client config
  in `__init__` and only touch the disk on start).
- **Confidence:** HIGH.

### AR-067 — `Manager` decorator's `cleanup` parameter is dead code

- **Status:** ✅ RESOLVED (2026-09-09)
- **Severity:** LOW
- **Evidence:** `manager/__init__.py:38-53` (`Manager(..., cleanup=None)`),
  invoked in `manager/runtime.py:119-121` (`if manager.cleanup:
  await manager.cleanup(self.worker)`). A grep for `cleanup=` in `src/` finds no
  `@Manager` that passes it.
- **Problem:** A public extension seam with no callers and no test coverage. It
  enlarges the `Manager` interface and the `run_manager` `finally` logic for a
  capability nothing uses.
- **Why it matters:** Dead surface invites confusion about whether manager-level
  cleanup is a supported pattern.
- **Decision:** Keep the seam. The user chose the keep+test path over removal —
  manager-level cleanup is a legitimate teardown hook, and the parameter is
  exercised by `run_manager`'s `finally` block, so it should be covered rather
  than deleted.
- **Resolution:** Added `examples/manager_cleanup.py` (a `@Manager(name=...,
  cleanup=...)` whose cleanup callable performs visible teardown, run via
  `python -m examples.manager_cleanup`) and
  `test_cleanup_callable_runs_on_clean_shutdown` in `tests/test_manager_restart.py`,
  which asserts the cleanup callable runs on a clean (non-raising) shutdown —
  distinct from the existing raising-cleanup test. 142 tests pass.
- **Confidence:** HIGH (unused), LOW (harm).

### AR-068 — Manager discovery via MRO `__dict__` reflection is fragile

- **Severity:** LOW
- **Evidence:** `manager/runtime.py:39-60` (`iter_manager_definitions` walks
  `cls.__dict__` for `Manager` instances, deduping by `attribute.name or
  attribute_name`).
- **Problem:** Discovery is stringly-named and rename-sensitive: renaming a
  decorated method changes its manager identity; a subclass that overrides a
  manager method *without* the decorator will not shadow the base `Manager`
  instance; and two unrelated managers that independently pick the same `name=`
  silently collide (first in MRO wins).
- **Why it matters:** Implicit registration by reflection is surprising and
  hard to grep; the failure modes are silent.
- **Recommendation:** Prefer an explicit registration mechanism, or at least
  warn on a name collision rather than silently dropping one manager.
- **Confidence:** MEDIUM.

### AR-069 — `_config` re-store / double-instantiation pattern in subclass constructors

- **Severity:** LOW
- **Evidence:** `task_processor.py:74-78` and `valkey/worker.py:102-107` both
  call `super().__init__(config)` (which stores a config) and then overwrite
  `self._config` with a locally re-created `TaskProcessorConfig()`/
  `ValkeyWorkerConfig()` when `config is None`.
- **Problem:** The base constructor cannot know the concrete config type, so
  subclasses re-instantiate a default and overwrite the field. When `config is
  None`, a `WorkerConfig()` is constructed and immediately discarded, then the
  subclass reconstructs its own default. This is a mild violation of the
  template-method expectation and duplicates default-construction logic.
- **Why it matters:** It is subtle and easy to get wrong (each subclass must
  remember to re-store); a future config field read before the re-store would
  silently see the wrong struct.
- **Recommendation:** A class-level `_config_type`/`_default_config()` factory
  so `BasicWorker` stores the correct concrete type and subclasses don't
  re-store.
- **Confidence:** HIGH.

### AR-070 — `LoggingLifecycle.register_logger_handler` retains an unused `name` parameter

- **Severity:** LOW
- **Evidence:** `logging/lifecycle.py:37-43` (the `name` parameter is documented
  as unused), still passed by `valkey/worker.py:184`
  (`register_logger_handler(self._valkey_logger_handler, name="AsyncValkeyHandler")`).
- **Problem:** Leftover from the AR-045 wrapper removal; the caller still passes
  a value that is ignored. Statuses are keyed by `handler.name`/
  `handler.__class__.__name__` instead.
- **Why it matters:** A misleading signature (callers may believe the name is
  meaningful) and an unclosed tail from the previous review (AR-031/H18).
- **Recommendation:** Drop the `name` parameter and its one argument site.
- **Confidence:** HIGH.

### AR-071 — White-box test coupling to private internals

- **Severity:** LOW
- **Evidence:** `tests/test_valkey_worker.py:93/227/236/251/268/283/313/347/380`
  (assign `worker._client`, mutate `worker._task_entry_ids`),
  `tests/test_manager_restart.py:120-233` (mutate
  `worker._manager_runtime.tasks`), `tests/test_basic_worker.py:56`
  (`worker._logging_lifecycle.statuses`).
- **Problem:** Tests reach into private instance state (`_client`,
  `_task_entry_ids`, `_manager_runtime`, `_logging_lifecycle`) to arrange
  scenarios, binding the suite to internals that are legitimate refactor
  targets. The AR-045/046 refactors required repointing many tests for exactly
  this reason.
- **Why it matters:** White-box tests raise the cost of the internal
  simplifications recommended here (AR-059, AR-061) and can mask contract
  drift by testing implementation rather than behavior.
- **Recommendation:** Where feasible, drive tests through public seams
  (`add_task_handler`, `enqueue_task`, `connect`/`disconnect`, the worker's
  read-only views) and reserve internal access for the few genuinely
  white-box cases (cancellation/requeue ordering).
- **Confidence:** MEDIUM (it is a deliberate trade-off for determinism).

## Cross-Cutting Analysis

### Dependency chains
The main chains are healthy: task path (transport → msgpack → `TaskData` →
`process_task` → handler → `TaskResult`), config path (`conf_dir` →
`read_valkey_config` → `ValkeyConfig` → `generate_glide_config` →
`GlideClientConfiguration`), log path (worker logger → external handlers), and
manager chain (`@Manager` → MRO scan → `run_manager` loop). The two structural
defects are (a) the intra-package `__init__ ↔ submodule` cycles (AR-065) and
(b) the stdlib-name shadowing across the `logging` subpackage (AR-056, now
resolved by renaming it to `log_handlers`), both of which are *naming/namespace*
problems rather than design-intent problems.

### Responsibility leakage
The clearest leakage is logging-handler lifecycle: it is split between the
generic `LoggingLifecycle` and the transport-specific `ValkeyWorker.connect`/
`cleanup`, with the worker reaching into external-handler internals (AR-061,
resolved — the handler now owns its own connection and the worker stops poking
`.client`). A secondary leak is connection teardown: intake (`fetch_tasks`) can
tear down a client that three other components are using (AR-059, resolved —
connect/disconnect are lock-serialized and reconnect is glide-error-only).

### Lifecycle / resource ownership
Worker lifecycle is strong (guarded transitions, forced terminal states). The
manager sub-lifecycle now records `RUNNING` (AR-057 resolved) and ends a
give-up manager in terminal `FAILED` (AR-063 resolved). Client ownership is now
single-owner and lock-serialized, with the logging handler on a separate
connection (AR-059 resolved). Construction is not side-effect-free
for `ValkeyWorker` (AR-066).

### State management
Per-worker state is well-encapsulated (name-mangled, read-only `MappingProxyType`
views). No module-level mutable global state. The remaining wart is the
`_config` re-store pattern (AR-069).

### Async/concurrency boundaries
Cancellation, requeue, and ack ordering are carefully handled. Timeout math now
uses `time.monotonic()` (AR-058 resolved); shared-client mutation across tasks
is now lock-serialized with a glide-error-only reconnect (AR-059 resolved). The
`XAUTOCLAIM` recovery adds a cross-process concurrency hazard (duplicate
processing) with no lease (AR-060).

### Abstractions crossing package boundaries
Two cross-package abstractions deserve scrutiny: (1) the external
`scietex.logging` handlers — the worker previously reached into
`AsyncValkeyHandler` internals (`.client`, `logging_running_event`) beyond the
`start_logging`/`stop_logging` seam (AR-061, resolved — the handler is now
handed `valkey_config=` and owns its own connection); (2) `TaskData` crossing
the transport boundary as the wire format itself, with no envelope (AR-064).

### Observability
The single weakest cross-cutting dimension. Manager status is now recorded
(AR-057 resolved) and manager death is now observable — a give-up manager ends
in terminal `FAILED` surfaced through `failed_managers` (AR-063 resolved) — but
the `_config`/`statuses`/`errors` bookkeeping is still not surfaced through any
documented read-only API beyond the new accessor.

## Architectural Recommendations

### Priority 1 — fix first
1. **AR-056** — stop the stdlib `logging` shadowing in the package namespace
   (alias the stdlib reference or rename the subpackage). Blocks core-only
   installs; one-line-class fix. — **DONE** (2026-09-09): renamed the in-package
   subpackage to `log_handlers` (commit `64daf94`).
2. **AR-057** — record `ManagerStatus.RUNNING` and make `start_manager`'s guard
   status-aware. Cheap, unlocks real observability. — **DONE** (2026-09-09):
   `run_manager` records `RUNNING`; `start_manager` guard is status-aware.
 3. **AR-058** — switch task-timeout tracking to `time.monotonic()`. One-line
    correctness fix. — **DONE** (2026-09-09): `TaskTracker.started` and the
    watchdog's `now` now use `time.monotonic()`.

### Priority 2 — important
4. **AR-063** — surface manager failure/death to the worker (aggregate health
   accessor or a fail-fast policy for critical managers). — **DONE** (2026-09-09):
   a give-up manager ends in terminal `FAILED`, exposed via `failed_managers`
   and a CRITICAL watchdog log (observe + log; no auto-shutdown, per the
   approved design).
5. **AR-061** — make `LoggingLifecycle` the sole handler-lifecycle owner;
   construct/register the Valkey handler before `start_handlers`, inject the
   client through a narrow public seam. — **DONE** (2026-09-09): the handler is
   handed `valkey_config=` and owns its own connection; the worker no longer
   injects or re-points `handler.client`.
 6. **AR-062** — promote task-level timing constants into the config structs so
    the config object is the complete, single source of tuning knobs. —
    **DONE** (2026-09-09): `task_timeout`, `task_queue_fetch_timeout`,
    `task_cancellation_timeout` (on `TaskProcessorConfig`) and
    `claim_min_idle_ms` (on `ValkeyWorkerConfig`) now carry the MIN/MAX/DEFAULT
    treatment; the module constants were removed.
7. **AR-059** — serialize client connect/disconnect behind a single transport
   owner, or introduce a versioned client handle so concurrent users detect
   staleness. — **DONE** (2026-09-09): `connect`/`disconnect` are serialized
   behind an `asyncio.Lock`; intake reconnects only on glide errors.

### Priority 3 — opportunistic
8. **AR-060** — add a per-entry liveness signal (or configurable claim floor
   derived from max handler duration) and document the duplicate-processing
   exposure.
9. **AR-065** — drop the unused re-exports and eliminate the intra-package
   circular imports.
10. **AR-066** — defer config-file default creation to `start()`/`initialize()`.
11. **AR-068** — make manager discovery explicit or warn on name collisions.
    (AR-067 is **done** — the `Manager.cleanup` seam is kept and now covered by
    a test + example, not removed.)
12. **AR-064** — introduce a versioned transport envelope ahead of any schema
    evolution.
13. **AR-069/070/071** — clean up the `_config` re-store pattern, remove the
    unused `name` parameter, and gradually de-white-box the tests.

## Suggested Target Architecture

The current structure is already close to target; the changes are
simplifications and ownership fixes rather than a rebuild. The main additions:
a **Transport/Connection** component that is the sole client owner, a
**manager health signal** flowing out of `ManagerRuntime`, and **single-owner
logging lifecycle**.

```mermaid
graph TD
    subgraph Core["scietex.service (core)"]
        BW[BasicWorker<br/>identity + state machine + hooks]
        MR[ManagerRuntime<br/>discovery + loop + HEALTH]
        LL[LoggingLifecycle<br/>sole handler-lifecycle owner]
        TP[TaskProcessor<br/>queue + dispatch + watchdog (monotonic)]
        TH[TaskHandler + Context<br/>task_handler subpackage]
        BW --> MR
        BW --> LL
        TP --> BW
        TP --> TH
        MR -. manager death .-> BW
    end

    subgraph Feature["Valkey transport (optional)"]
        VW[ValkeyWorker]
        VC[ValkeyConfig]
        CONN[Connection/Transport<br/>sole GlideClient owner]
        VW --> TP
        VW --> CONN
        VW --> VC
        CONN --> GLIDE[valkey-glide]
    end

    ENV[Envelope<br/>versioned wire format] --> VW
    TH -. TaskData .-> ENV

    style Core fill:#e8f0e8
    style Feature fill:#f0e8e8
```

**Target changes:**
- A **Connection/Transport** component owns `GlideClient` create/close and
  publishes a stable/versioned handle, so intake reconnect no longer reassigns
  shared state under concurrent users (AR-059 — **done** via `_client_lock`
  serialization and glide-error-only reconnect).
 - `ManagerRuntime` records `RUNNING` (**done**, AR-057 resolved) and exposes an
   aggregate health/error signal the worker can act on (**done**, AR-063 resolved:
   `FAILED` terminal state surfaced through `failed_managers`).
- `LoggingLifecycle` is the single owner of *all* async logging handlers;
  `ValkeyWorker` only injects the client via a narrow seam (AR-061 — **done**:
  the handler now owns its own connection via `valkey_config=`, so no client
  injection is needed in the typed-config path).
- Task timing moves into the config structs (AR-062 — **done**: `task_timeout`,
  `task_queue_fetch_timeout`, `task_cancellation_timeout`, `claim_min_idle_ms`);
  timeout math is monotonic
  (**done**, AR-058 resolved).
- The in-package `logging` subpackage is renamed to `log_handlers` to
  eliminate the namespace shadowing (AR-056) — **done** (commit `64daf94`).
- A versioned transport envelope decouples the durable wire format from
  `TaskData` (AR-064).

## Migration Strategy

Safe, incremental, dependency-ordered:

1. **Phase 1 — correctness (no API change):** AR-056 (namespace shadowing) is
   **done** (commit `64daf94`); AR-057 (RUNNING status) is **done** (2026-09-09);
   AR-058 (monotonic clock) is **done** (2026-09-09). Each is small, isolated, and
   immediately testable.
2. **Phase 2 — observability:** AR-063 (manager death signal) is **done**
   (2026-09-09): a `FAILED` terminal state surfaced through `failed_managers`,
   with a CRITICAL watchdog log. Depends on AR-057.
3. **Phase 3 — ownership consolidation:** AR-061 (single logging-lifecycle
   owner) and AR-059 (connection ownership) are **done** (2026-09-09): the
   handler owns its own connection via `valkey_config=`, and the operational
   client is lock-serialized with a glide-error-only reconnect. The larger
   refactors were the two-domain split of the logging handler onto its own
   connection and the lock-serialized connect/disconnect.
4. **Phase 4 — configuration completion:** AR-062 (promote timing constants into
   config) is **done** (2026-09-09); then AR-066 (defer config default creation
   to start).
5. **Phase 5 — cleanup / hardening:** AR-065 (drop circular imports),
   AR-068 (manager discovery), AR-069/070 (config re-store, unused param),
   AR-071 (de-white-box tests as seams stabilize). AR-067 (the `Manager.cleanup`
   seam) is **done** — kept and covered by a test + example, not removed.
6. **Phase 6 — future evolution:** AR-064 (versioned envelope) and AR-060
   (per-entry lease) — defer until the wire format or scale-out load actually
   changes.

Phases 1–4 are independent of 5–6; only Phase 2 depends on Phase 1.

## Open Questions

1. **Scale-out reality:** Is the multi-replica shared-queue model actually
   deployed, or is `ValkeyWorker` effectively used as a single consumer? This
   determines the real severity of AR-060 (duplicate processing).
2. **Handler duration distribution:** What are typical handler execution times?
   This determines a safe `DEFAULT_CLAIM_MIN_IDLE_MS`/lease design (AR-060) and
   whether the 3 s default task timeout (AR-062) is even viable.
3. **Manager-failure policy:** Should a permanently failing manager fail the
   worker (crash) or degrade it (log + continue)? This is an operator-policy
   decision behind AR-063 — **resolved (2026-09-09)** as observe + CRITICAL log,
   no auto-shutdown; a fail-fast policy for critical managers remains a future
   option.
4. **`scietex.logging` stability:** Is the external package's `AsyncValkeyHandler`
   `.client`/`logging_running_event` considered public API? This determines how
   urgent the AR-061 seam cleanup is.
5. **Wire-format evolution horizon:** Is a versioned task envelope (AR-064)
   needed now, or is the durable queue effectively disposable (purgeable)
   across upgrades?
