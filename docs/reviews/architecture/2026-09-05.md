# Architecture Review — Follow-up

**Date:** 2026-09-05
**Package:** `scietex.service` v2.0.0
**Baseline:** commit `eed7dca`; prior review `docs/reviews/architecture/2026-09-04.md`
**Scope:** Re-assessment after fixes for **AR-001, AR-002, AR-004** (uncommitted working-tree changes to `basic_async_worker.py`, `manager.py`, `valkey_async_worker.py`, plus new `tests/test_manager_restart.py`).

---

## Executive Summary

The three highest-leverage correctness findings from the 2026-09-04 review have
been **fixed and verified**. The manager runtime no longer self-cancels on error
(AR-001), subclass manager overrides now work as documented and the decorator is
a proper descriptor (AR-002), and the logging lifecycle is resumable across
`STOPPED → RUNNING` restarts (AR-004). All changes are internal — no public API
was broken — and are covered by new tests. Lint, format, type-check, and the
full test suite (20 tests) pass.

The single most important cross-cutting conclusion of the prior review — that a
worker instance is effectively **one-shot** because the advertised
`STOPPED → RUNNING` restart path did not work — is now **resolved**. A worker
can be stopped and restarted, its async logging handlers are re-created, and a
failing manager retries with bounded backoff instead of silently dying.

The remaining findings (AR-003, AR-005, AR-006, AR-007, AR-008, AR-009, AR-010,
AR-011, AR-012, AR-013, AR-014, AR-015, AR-016) are **unchanged and still open**.
The most important of these are now the reliability gaps that dominate the
framework's risk profile: the undefined task delivery/ack/retry contract
(AR-005), the dual-`GlideClient` connection-state asymmetry (AR-006), and the
`BasicAsyncWorker` god class (AR-003).

**Next fix candidates:** AR-006 (connection-state symmetry), AR-005 (task
delivery contract), AR-010 (error boundaries). These are the remaining
correctness/reliability items that keep the framework from being safe to run
unattended.

## What Changed (AR-001, AR-002, AR-004)

### AR-001 — Manager restart self-cancellation: FIXED

**Prior problem:** `_run_manager` called `_restart_manager` from inside the
failing manager's own task; `_stop_manager` cancelled and awaited the currently
executing task, delivering `CancelledError` (a `BaseException`, not caught by
`except Exception`), unwinding the coroutine so `_start_manager` never ran and
leaving a stale `__manager_tasks` entry.

**Fix (verified in `basic_async_worker.py`):**
- `_run_manager` (634–697) is now an **in-task retry loop**. A single task loops
  calling `manager.method(self)`; on a non-`CancelledError` exception it records
  the error in `__manager_errors`, increments a consecutive-failure counter, and
  either retries after `manager_restart_backoff` or, once the counter exceeds
  `manager_max_retries`, logs "Giving up" and breaks. A successful iteration
  resets the counter.
- The `finally` block (688–697) runs `manager.cleanup`, marks the manager
  `STOPPED`, and removes the task from tracking via
  `if self.__manager_tasks.get(name) is asyncio.current_task(): pop(...)` — so a
  later `_start_manager` for the same name works.
- `_stop_manager` (720–740) now uses `pop(name, None)` instead of `del`, so it
  is safe whether or not the task already removed itself.
- The now-unused `_restart_manager` method was removed.
- New clamped constructor kwargs/properties: `manager_max_retries` (default 5,
  range 0–100) and `manager_restart_backoff` (default 1 s, range 0–60), with
  module constants `DEFAULT_MANAGER_MAX_RETRIES`/`DEFAULT_MANAGER_RESTART_BACKOFF`.

**Assessment:** The fix is sound and matches the prior recommendation (replacement
rather than in-place stop/start, bounded retry/backoff, clean bookkeeping). The
retry happens inside the same task rather than spawning a fresh task, which is a
valid and simpler realization of the "replacement" intent — the key property
(never cancelling/awaiting one's own task) is satisfied. A persistently failing
manager now degrades observably (ERROR logs, then give-up) instead of spinning or
silently dying.

**Residual note:** When a manager gives up, the worker continues to report
`RUNNING` with that subsystem stopped. This is now *observable* (ERROR log +
`__manager_errors[name]` set + task removed from `__manager_tasks`), but there is
still no mechanism to propagate a manager give-up into the worker's overall state
(e.g. transition to a failed/stopping state). This is a design decision worth
making explicit (see Open Questions).

### AR-002 — Discovery order + leaky decorator: FIXED

**Prior problem:** (1) `_iter_manager_definitions` iterated
`reversed(type(self).__mro__)` (base-first), so a subclass override of a
same-named manager was silently skipped. (2) `Manager.__call__` returned `self`,
replacing the class attribute with a `Manager` instance, so the decorated method
was not callable as a normal method.

**Fix (verified):**
- `_iter_manager_definitions` (488–509) now iterates `type(self).__mro__`
  **most-derived-first** and dedupes by manager name via a `seen` set, so a
  subclass override of a same-named manager shadows the base definition.
- `Manager` (`manager.py`) is now a **proper descriptor**: `__get__` (75–94)
  returns `self` when accessed on the class or when `method` is unset, otherwise
  returns `MethodType(self.method, instance)`. Decorated methods are therefore
  callable as normal bound methods (`self._heartbeat_manager()`) while the class
  attribute still holds the `Manager` instance for discovery. `__call__`'s return
  annotation was corrected to `"Manager"`.

**Assessment:** Both halves of the finding are resolved. Discovery order now
matches the docstrings, and the decorator is no longer a leaky abstraction —
typing, introspection, and direct method calls all behave as expected. The
`seen`-set dedup is a clean way to make name-keyed bookkeeping consistent with
override semantics.

### AR-004 — Logging lifecycle not resumable: FIXED

**Prior problem:** `_logger_shut_down_handlers` recorded handlers as `RUNNING`
after stopping them, and external `AsyncBaseHandler`s are single-use once
`stop_logging()` closes them, so a restarted worker produced no log output.

**Fix (verified):**
- `_logger_shut_down_handlers` (595–622) now records
  `__loggers_statuses[handler_name] = LoggerStatus.STOPPED` (line 622).
- A **handler-factory registry** was added: `_register_logger_handler(factory,
  name=None)` (523–544) creates a handler, records its factory in
  `__logger_handler_factories`, and attaches it to the logger.
  `BasicAsyncWorker.__init__` registers the console `AsyncBaseHandler` factory
  (145–147); `ValkeyWorker.__init__` registers the `AsyncValkeyHandler` factory
  (`valkey_async_worker.py:139`).
- `_logger_start_handlers` (546–593) iterates a copy of `logger.handlers`; when a
  handler's recorded status is `STOPPED` (closed in a prior shutdown) and a
  factory exists, it removes the old handler, creates a fresh replacement via the
  factory, and starts the replacement.

**Assessment:** This resolves the resumability gap and, together with AR-001,
makes the `STOPPED → RUNNING` restart path actually work. The factory-registry
design is clean and correctly scoped to the single-use nature of the external
handlers. The `_logger_start_handlers` mutation of `logger.handlers` while
iterating is correctly handled by iterating a `list(...)` copy.

### Cross-cutting note on the "one-shot worker" conclusion

The prior review's central cross-cutting finding — that AR-001 + AR-004 + AR-007
combined to make worker instances effectively one-shot — is now **largely
resolved** for the restart path: AR-001 and AR-004 are fixed, so a stopped worker
can be restarted with working managers and logging. AR-007 (managers start before
`initialize()`) remains, but it is a *startup-ordering* concern (a race for
managers depending on `initialize()`-created resources), not a restart blocker.
The restart path itself is now reliable.

## Open Questions (updated)

1. **Should a manager give-up propagate to the worker's overall state?** With
   AR-001 fixed, a persistently failing manager now stops observably but the
   worker stays `RUNNING`. Decide whether a manager give-up should transition the
   worker to a failed/stopping state or remain a per-manager concern.
2. **Are worker instances intended to be restartable?** Now that AR-001 and
   AR-004 are fixed, the implementation *does* support restart. This question is
   effectively answered "yes" by the code; confirm the docs match.
3. **What is the delivery guarantee target?** Exactly-once, at-least-once, or
   best-effort? This determines the ack/result-sink and dedup design for AR-005.
4. **Is a single shared `GlideClient` acceptable to the external
   `scietex.logging` package?** AR-006's cleanest fix depends on the external
   handler's ownership contract, which lives outside this repo.
5. **Is `pyaml` required transitively by `scietex.logging`?** Could not be
   confirmed from this repo; affects AR-013.
6. **Are multiple workers per process a real requirement?** Affects signal
   ownership (AR-015) and whether the framework should drop the
   single-worker-per-loop assumption.
7. **Is the control/PubSub path (`listening=True`) a planned feature?** It is
   currently dead code in `valkey_config.py`; unclear whether to keep, finish, or
   remove.
