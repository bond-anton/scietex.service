# Architecture Review

**Date:** 2026-09-04
**Package:** `scietex.service` v2.0.0
**Baseline:** commit `eed7dca`, architectural map in `docs/architecture/`

---

## Executive Summary

The architecture is **directionally sound but not reliable as shipped**. The
fundamental shape — a three-level worker hierarchy (`BasicAsyncWorker` →
`AsyncTaskProcessor` → `ValkeyWorker`) built on a manager-loop runtime, with an
optional Valkey transport isolated behind an optional-import boundary and a
pluggable handler contract defined by frozen `msgspec` schemas — is coherent,
cleanly layered, and mostly free of circular dependencies. The dependency
direction (feature → core, never core → feature) and the `task_handler` boundary
(via `TYPE_CHECKING`) are genuinely good decisions.

However, the **runtime's central advertised feature is broken**: the "automatic
manager restart on error" path self-cancels the manager it is trying to restart,
so any transient exception in a manager (Heartbeat, Watchdog, TaskManager,
TaskQueueManager) permanently kills that manager while the worker continues to
report `RUNNING`. This is verified experimentally (see AR-001). Combined with a
non-resumable logging lifecycle (AR-004) and stale manager-task bookkeeping, a
worker instance is effectively **one-shot**: the `STOPPED → RUNNING` transition
that the state machine advertises does not actually work.

The strongest aspects are the clean vertical layering, the typed immutable
schemas, the decoupled Valkey config schema, and the uniform async-logging
handler lifecycle. The most important weaknesses are: (1) the broken manager
restart, (2) the oversized `BasicAsyncWorker` "god class", (3) the ill-defined
task result/ack/retry contract, and (4) several correctness gaps around
connection state and error boundaries.

**Fix first:** AR-001 (manager restart), AR-004 (logging lifecycle), AR-006
(connection-state symmetry / dual client). These are correctness/reliability
issues that make the framework unsafe to run unattended.

## Architecture Assessment

| Dimension | Assessment |
|---|---|
| **Boundaries** | Good. Valkey is cleanly isolated (`valkey/` subpackage); core never imports Valkey; `task_handler` has no runtime back-reference to the worker. Public surface is centralized in `__init__.py`. |
| **Responsibilities** | Weak. `BasicAsyncWorker` bundles identity, lifecycle state machine, signal handling, logging-handler lifecycle, the entire manager-task runtime, and default domain hooks into one ~770-line class (AR-003). |
| **Dependencies** | Good direction, clean acyclic graph. One caveat: `task_handler` handlers receive the *whole worker* and can reach its internals (AR-009). |
| **Abstractions** | Mixed. The `Manager` decorator is a leaky abstraction (returns `self`, replaces the method attribute); the `TaskHandler` ABC is clean but its `supported_tasks` vs. registration-name duality is confusing (AR-009). |
| **Lifecycle** | Fragile. State machine exists and is well-named, but restart-on-error is broken (AR-001), logging is one-shot (AR-004), managers start before `initialize()` (AR-007), and shutdown cancellation is not rolled back (AR-010). |
| **Concurrency** | Single-loop cooperative asyncio is the right call for this scope, but the task lifecycle leaks: results are dropped, tasks can outlive their `running_tasks` entry, and unretrieved task exceptions accumulate (AR-005, AR-010). |
| **State ownership** | Weak encapsulation. `events`, `task_handlers`, `running_tasks`, `task_queue` are handed out by reference; consumers mutate them directly (AR-008). Connection state is split across two owners (AR-006). |
| **Testability** | Moderate. Core processor logic is testable, but real-time `asyncio.sleep` in tests, broken test mocks (AR-014), and the requirement to construct inside a running loop (AR-015) raise the cost. |
| **Extensibility** | Moderate. Subclass hooks (`initialize/heartbeat/watchdog/cleanup`, `fetch_tasks/return_task_to_queue`, `@Manager`) are the right idea, but manager *override* is broken by base-first discovery (AR-002) and handler recovery options are too coarse (AR-005). |

## Strengths

1. **Clean vertical layering with correct dependency direction.** `ValkeyWorker
   → AsyncTaskProcessor → BasicAsyncWorker → Manager`; core modules never import
   Valkey, and `valkey_config` is independent of the worker. This is exactly the
   direction you want for an optional transport.
   (`dependencies.md`; verified in `basic_async_worker.py`, `async_tasks_processor.py`, `valkey/`.)

2. **Guarded optional-import boundary.** `src/scietex/service/__init__.py:24-53`
   isolates the Valkey surface so the core package imports without `valkey-glide`.
   (The broad `except Exception` is a deliberate, documented trade-off — see AR-013 note.)

3. **`task_handler` boundary with no runtime cycle.** The handler ABC keeps its
   only worker reference under `TYPE_CHECKING`
   (`task_handler/basic.py:9-10`), avoiding a worker↔handler import cycle.

4. **Frozen typed schemas as the single wire/contract source.** `msgspec.Struct`
   schemas (`task_handler/schemas.py`, `valkey/schemas.py`) give immutability and
   msgpack/YAML serialization from one definition.

5. **Decoupled configuration schema.** `valkey_config.py` is a typed schema +
   loader + schema→glide converter that can be unit-tested without a worker or a
   live server (confirmed by `tests/test_valkey_config.py`).

6. **Uniform async-logging handler lifecycle.** The worker drives all
   `AsyncBaseHandler`s (console and Valkey) through the same
   `start_logging()`/`stop_logging()` path with per-handler timeouts
   (`basic_async_worker.py:429`, `:465`). The *idea* is right even though the
   resumability is broken (AR-004).

7. **Centralized config-dir resolution.** `utils/conf.py` implements a single,
   well-documented precedence chain (`conf_dir` → env → XDG → /etc → CWD → create
   default) rather than scattering it.

## Critical Issues

### AR-001 — Manager "automatic restart on error" self-cancels the manager and permanently kills it

**Severity:** CRITICAL

**Evidence**
- `basic_async_worker.py:504-537` (`_run_manager`): on a non-`CancelledError`
  exception the code records the error and calls `await self._restart_manager(name, manager)`.
- `basic_async_worker.py:580-589` (`_restart_manager`): calls `_stop_manager`
  then `_start_manager`.
- `basic_async_worker.py:560-578` (`_stop_manager`): calls
  `self.__manager_tasks[name].cancel()` and then
  `await asyncio.wait_for(self.__manager_tasks[name], ...)` — i.e. it cancels and
  awaits the **currently executing task itself**.
- Verified by a controlled experiment: a `@Manager` method that raises
  `RuntimeError` ends with `ManagerStatus.STOPPED`, `__manager_errors[name] ==
  RuntimeError`, the task still present in `__manager_tasks` (the `del` at line 578
  is never reached), and **no replacement task is created**. The loop does not
  restart.

**Problem**
The restart path operates on the manager's own task from inside that task's
exception handler. `cancel()` schedules a cancellation; the subsequent
`await` of the same task delivers `CancelledError` (which, being a
`BaseException`, is not caught by the surrounding `except Exception`), unwinds
the coroutine, and the `finally` block marks the manager `STOPPED`. The intended
"stop then start again" never reaches `_start_manager`. Additionally, because
`_stop_manager` is cancelled mid-await, `del self.__manager_tasks[name]` never
executes, leaving a stale entry that makes any later `_start_manager` skip the
name (`basic_async_worker.py:547-549`).

**Why it matters**
- Any transient error in Heartbeat, Watchdog, TaskManager, or TaskQueueManager
  silently stops that subsystem while the worker still reports `RUNNING`. For a
  daemon this is the worst failure mode: no crash, no log at ERROR beyond the
  initial "Restarting", just silent cessation of work.
- The stale `__manager_tasks` entry prevents the same name from ever starting
  again on that instance, compounding AR-004 to make the instance unrecoverable.

**Recommendation**
Re-design the manager restart as a *replacement* rather than an in-place
stop/start of the running task: on error, spawn a fresh `_run_manager` task and
record it under the name, never awaiting/cancelling the currently running task
from within itself. Add a backoff and a max-retry policy so a persistently
failing manager degrades observably instead of spinning. Fix the stale-entry
bookkeeping in `_stop_manager`.

**Confidence:** HIGH (reproduced experimentally)

## Major Issues

### AR-002 — Manager discovery order is inverted vs. documented, and name-keyed bookkeeping breaks subclass overrides; the decorator is a leaky abstraction

**Severity:** HIGH

**Evidence**
- `basic_async_worker.py:402-415` (`_iter_manager_definitions`) iterates
  `reversed(type(self).__mro__)` — base classes first. The docstrings of
  `_iter_manager_definitions`, `_start_managers`, and `_stop_managers` all claim
  "most-derived to base".
- `basic_async_worker.py:547-549` (`_start_manager`) skips any manager whose name
  already exists in `__manager_tasks`.
- `manager.py:57-72` (`Manager.__call__`) stores the method and returns `self`,
  so the decorated method's class attribute is replaced by a `Manager` instance,
  not by the method.

**Problem**
(1) Discovery order is base-first, so if a subclass overrides a manager method
and re-applies `@Manager` with the same name, the base manager starts first and
the subclass's version is silently skipped ("already running"). The documented
override semantics are inverted and effectively broken for same-named managers.
(2) The decorator returning `self` means a decorated method is no longer callable
as a method (`self._heartbeat_manager()` would invoke `Manager.__call__` with no
argument), and `_run_manager` must invoke it as `await manager.method(self)`
(line 522) — bypassing normal method binding.

**Why it matters**
- Extension through manager overrides is a core advertised capability; the
  current behavior is the opposite of the documentation and can only be
  discovered at runtime by inspection.
- The non-callable decorator is a leaky abstraction that confuses tooling,
  typing, and introspection, and makes the "method" harder to reason about than
  a plain descriptor-based decorator.

**Recommendation**
Iterate MRO most-derived-first (drop the `reversed(...)`). Store the manager
method as a proper descriptor/bound callable rather than a plain function held
on a decorator instance. Consider keying manager bookkeeping by identity (class +
name) or disambiguating name collisions explicitly so a derived manager can
replace a base one.

**Confidence:** HIGH

### AR-003 — `BasicAsyncWorker` is a god class mixing service container, machinery, and domain hooks

**Severity:** HIGH

**Evidence**
- `src/scietex/service/basic_async_worker.py` — `BasicAsyncWorker` spans lines
  58–827 and owns: identity/config (82–168), lifecycle state machine
  (`_startup` 611, `_shutdown` 679), signal handling (417–427), logging-handler
  lifecycle (429–492), the entire manager runtime (`_run/_start/_stop/_restart_manager`
  504–609), and default heartbeat/watchdog/cleanup hooks (774–827).

**Problem**
A single class is simultaneously the service container, the concurrency runtime,
the logging subsystem manager, and the domain extension surface. Every subclass
inherits all of it, and the domain hooks are interleaved with the machinery in
the same namespace.

**Why it matters**
- Change amplification: any edit to manager runtime, logging, or state-machine
  logic risks touching behavior unrelated to the change.
- Testability: you cannot exercise the manager runtime without constructing a
  full worker (which requires a running event loop and registers signal
  handlers — AR-015).
- Reasoning cost: the class has no clear internal seam, so contributors cannot
  extend or debug one concern in isolation.

**Recommendation**
Extract a `ManagerRuntime` (or `ManagerPool`) that owns discovery/start/stop/
restart of managers, and a small `LoggingLifecycle` coordinator, leaving
`BasicAsyncWorker` to orchestrate state and expose domain hooks. Keep the public
API stable; this is an internal refactor.

**Confidence:** HIGH

### AR-004 — Logging lifecycle is not resumable; a stopped worker cannot be restarted reliably

**Severity:** HIGH

**Evidence**
- `basic_async_worker.py:465-492` (`_logger_shut_down_handlers`) sets
  `__loggers_statuses[handler_name] = LoggerStatus.RUNNING` (line 492), not
  `STOPPED`, after stopping handlers.
- `basic_async_worker.py:440-443` (`_logger_start_handlers`) skips handlers whose
  recorded status is `RUNNING`.
- External `scietex.logging` `AsyncBaseHandler.stop_logging()` calls
  `self.close()` at the end, and `start_logging()` creates tasks from
  `self.log_workers` — coroutine objects that are single-use.

**Problem**
The worker's recorded handler status and the actual handler lifecycle are
inconsistent: after shutdown the handlers are closed, but the worker records them
as `RUNNING`, so a subsequent `start()` skips restarting them. Even if it did
not, the external handler cannot be restarted (its worker coroutines were
consumed and the handler was closed).

**Why it matters**
- The state machine advertises `STOPPED → RUNNING`, but a restarted instance
  produces no log output and, for `ValkeyWorker`, no Valkey log stream.
- Together with AR-001's stale manager entries, worker instances are effectively
  one-shot, contradicting the framework's own lifecycle contract.

**Recommendation**
Set `LoggerStatus.STOPPED` on shutdown; either re-create handlers on restart or
make the external handlers restartable (re-initialize worker coroutines on
`start_logging`). Decide explicitly whether instances are restartable or
single-use and make the state machine and docs match that decision.

**Confidence:** HIGH

### AR-005 — Task results are discarded and the distributed at-most-once/retry contract is undefined

**Severity:** HIGH

**Evidence**
- `async_tasks_processor.py:489-494` (`handle_task`) awaits `process_task` and
  discards the returned `TaskResult` (only a `finally` that pops and
  `task_done()`).
- `async_tasks_processor.py:433-474` (`process_task`) centralizes all failures
  into a stringly `TaskResult(status="error", error=str(e))`.
- `valkey_async_worker.py:423-432` (`fetch_tasks`) `XACK`s and `XDEL`s the stream
  entry **as soon as it enters the in-process queue**.
- `async_tasks_processor.py:530-569` (`watchdog`) cancels a timed-out task and
  re-queues it (`return_task_to_queue`) regardless of whether the handler
  actually stopped (a handler may swallow `CancelledError`).

**Problem**
There is no result sink, no ack to the transport on success, and no dedup/
ordering guarantee. The transport acknowledges-and-deletes on enqueue, so a
crash after enqueue loses the task; a timeout re-appends to the stream tail
(ordering lost) even if the original handler is still running, producing
duplicates. Recovery policy is concentrated in the processor's watchdog with no
per-task retry count, backoff, or partial-progress signal; the `TaskHandler`
contract (`handle`) cannot express "not done, retry" vs. "failed, discard".

**Why it matters**
- The "distributed task queue" semantics are effectively undefined: callers
  cannot rely on exactly-once, at-least-once, ordering, or result delivery.
- Task loss and duplicate processing are silent by default, which is dangerous
  for a daemon framework that consumers will trust.

**Recommendation**
Define the delivery/ack contract explicitly. At minimum: ack the transport on
handler completion (not on enqueue), add a result sink hook, and make requeue
conditional on the task actually having been cancelled. Consider a
retry-count/dead-letter concept and a structured error type. This is a design
decision that should be resolved before adding result consumers.

**Confidence:** HIGH

### AR-006 — `ValkeyWorker` owns two independent GlideClients with asymmetric connection-state handling

**Severity:** HIGH

**Evidence**
- `valkey_async_worker.py:139-147` constructs an `AsyncValkeyHandler`, which owns
  its own `GlideClient` (external `scietex.logging` `_worker` connects and
  disconnects it); `valkey_async_worker.py:192` creates a second client for
  task/heartbeat traffic.
- `valkey_async_worker.py:180-202` (`connect`): on `GlideClient.create`
  exception returns `False` and leaves `_client = None`; on a **failed PING**
  returns `False` but leaves `_client` set, so `initialize()` (line 268) proceeds
  as if connected.
- Reconnect logic exists only in `fetch_tasks`'s exception handler (436-437).

**Problem**
Two connection lifecycles must be torn down by two different owners (worker
`cleanup` vs. log-handler `stop_logging`), splitting failure modes and resource
accounting. The `connect()` return value is not a reliable connectivity signal:
a ping failure reports `False` but leaves a non-None client, which the
`initialize()` guard treats as success.

**Why it matters**
- Heartbeat/task-fetch later guard on `client` truthiness, so a half-connected
  worker enters `RUNNING` and then silently fails operations.
- Double connections to the same server complicate resource limits, TLS
  configuration duplication, and shutdown ordering.

**Recommendation**
Make `connect()` set `_client` only on verified success (clear it on ping
failure). Consolidate transport ownership — ideally a single shared client (or an
explicit connection pool abstraction) used by both tasks and logging, or at
minimum a single coordinator that owns both lifecycles with a single ordering
guarantee.

**Confidence:** HIGH

## Moderate Issues

### AR-007 — Managers start before `initialize()` completes

**Severity:** MEDIUM

**Evidence**
- `basic_async_worker.py:633-644` (`_startup`): `_logger_start_handlers` →
  `_start_managers` (636) → `initialize()` (639). `ValkeyWorker` connects to
  Valkey inside `initialize()`.

**Problem**
Manager tasks are running before the subclass `initialize()` hook returns.
Built-in managers defensively no-op until `start_time`/`client` are set, but
that safety is implicit and fragile.

**Why it matters**
A custom `@Manager` or task handler depending on `initialize()`-created
resources can race; correctness depends on ordering luck rather than an explicit
barrier.

**Recommendation**
Run `initialize()` before starting managers, or introduce an explicit
"ready" gate (e.g. `start_time`/`client`-driven barrier) that managers await.

**Confidence:** HIGH (mechanism); the harm is MEDIUM because built-ins already no-op.

### AR-008 — Internal mutable state is exposed by reference

**Severity:** MEDIUM

**Evidence**
- `basic_async_worker.py:180-191` (`events` property returns `self.__events`).
- `async_tasks_processor.py:152-182` (`task_handlers`, `running_tasks`,
  `task_queue` return the internal dicts/queue directly).
- Examples and tests mutate them (`examples/async_task_processor.py:172-174`,
  `tests/test_async_task_processor.py:73`).

**Problem**
Internal state (`__running_tasks`, `__task_queue`, `__events`) is handed out as
mutable references, so external code can corrupt invariants (e.g. unbalance
`task_done()` counts, clear the `exit` event, remove `running_tasks` entries).

**Why it matters**
- No single owner enforces queue/`task_done` accounting or event-state
  invariants, making subtle bugs possible and the class harder to evolve.
- It forces the public API to freeze on internal data structures.

**Recommendation**
Expose read-only views or explicit methods (`enqueue(task_id, data)`,
`wait_for_exit()`) and keep the mutable structures private. This is partly a
test-ergonomics trade-off; a narrow test-only enqueue API can replace direct
`task_queue.put`.

**Confidence:** MEDIUM

### AR-009 — Handler registry mixes registration names with supported task types; handlers receive the whole worker

**Severity:** MEDIUM

**Evidence**
- `async_tasks_processor.py:284-298` (`add_task_handler(name, class)`),
  `:353-369` (`_find_task_handler` iterates `task_handlers` and uses
  `handler.supports(task_type)`, ignoring the registration key).
- `task_handler/basic.py:24-35` (`TaskHandler.__init__(name, worker)` stores the
  full worker; `worker` is typed `BasicAsyncWorker` but only meaningful under
  `AsyncTaskProcessor`).

**Problem**
Two overlapping concepts (registration name vs. `supported_tasks`) coexist: the
name is used only for start/stop/remove/logging while dispatch is first-match by
`supports()`. A class may be registered under several names, and a single task
type may match several handlers with ambiguous precedence. Handlers are given the
entire worker, so they can reach `task_queue`, `running_tasks`, state, etc.,
coupling handler implementations to processor internals.

**Why it matters**
- The registration API is redundant/confusing and dispatch precedence is
  implicit ("first active wins").
- Handler implementations can bypass the `handle` contract and reach into
  processor state, making them harder to test in isolation and binding them to
  `AsyncTaskProcessor` internals.

**Recommendation**
Decide between name-based and type-based registration (or unify them), make
dispatch precedence explicit (e.g. error on ambiguity), and pass handlers a
narrow, defined context instead of the full worker.

**Confidence:** MEDIUM

### AR-010 — Error-handling boundaries leak: unretrieved task exceptions and swallowed initialization failures

**Severity:** MEDIUM

**Evidence**
- `async_tasks_processor.py:453-462` (`process_task` raises `ValueError` for an
  empty `task` field rather than returning an error `TaskResult`).
- `async_tasks_processor.py:489-494` (`handle_task` has only a `try/finally`; the
  exception from `process_task` propagates into a task that is never awaited
  except via cancellation).
- `async_tasks_processor.py:300-323` (`_start_task_handler` catches
  `TimeoutError` and logs, but `initialize()` at 383-395 still returns `True`
  regardless).

**Problem**
The one code path that raises (empty task type) escapes the centralized
error→`TaskResult` conversion, producing an unretrieved task exception. Handler
startup failures (timeout) do not fail `initialize()`, so a worker can report
`RUNNING` with a handler that never became ready (it will then reject tasks with
"No handler found").

**Why it matters**
- Unretrieved task exceptions pollute logs ("Task exception was never
  retrieved") and mask real errors.
- Initialization success is not a reliable signal; the `initialize() -> bool`
  contract is inconsistently enforced.

**Recommendation**
Convert the empty-task case into an error `TaskResult` (or a structured error),
ensure every created task is awaited or its exception consumed, and propagate
handler-startup failures into `initialize()` so the worker fails fast.

**Confidence:** HIGH

### AR-011 — Config load silently swallows any error and overwrites `valkey.yml` with defaults

**Severity:** MEDIUM

**Evidence**
- `valkey_async_worker.py:127-138` falls back to `read_valkey_config(self.conf_dir)`.
- `valkey_config.py:239-274` (`read_valkey_config`): on any decode error, returns
  `ValkeyConfig()` and **writes the defaults back over `valkey.yml`** (lines
  270-273).

**Problem**
A typo or schema mismatch in `valkey.yml` is silently replaced by defaults and
the user's file is overwritten, destroying the evidence of the misconfiguration
and any intentional non-default settings.

**Why it matters**
- Silent misconfiguration with data loss; production workers can start with
  wrong endpoints/credentials while logging nothing actionable.

**Recommendation**
Fail loudly on invalid config (raise with the parse error), or preserve the
original file and only emit a warning/derive defaults in-memory. Do not overwrite
user config as a side effect.

**Confidence:** HIGH

### AR-012 — `msgspec.Struct` timestamp defaults are evaluated once at import time

**Severity:** LOW

**Evidence**
- `task_handler/schemas.py:60` (`TaskResult.processed_at = datetime.now(timezone.utc)`).
- `valkey/schemas.py:38` (`Heartbeat.timestamp = datetime.now(timezone.utc)`).

**Problem**
These class-level defaults run once at import, so every `TaskResult`/`Heartbeat`
constructed without an explicit timestamp shares the module-import timestamp.

**Why it matters**
`processed_at` appears to be a per-instance value; handlers that omit it all
report the same (stale) timestamp. (Valkey heartbeat always passes an explicit
timestamp, so practical impact is limited to task results.)

**Recommendation**
Use `msgspec.field(default_factory=...)` or set the timestamp explicitly at
construction sites.

**Confidence:** HIGH

### AR-015 — Worker construction is coupled to a running loop, single worker per process, Unix-only

**Severity:** LOW

**Evidence**
- `basic_async_worker.py:417-427` (`_setup_signal_handlers`, called from
  `__init__`) uses `asyncio.get_running_loop()` and
  `loop.add_signal_handler(SIGINT/SIGTERM)`.
- `loop.add_signal_handler` is unavailable on Windows; later workers replace
  earlier signal registrations, so only the last-constructed worker reacts to
  signals.

**Problem**
Workers cannot be constructed outside a running loop; the framework implicitly
assumes one worker per process and a POSIX platform.

**Why it matters**
- Impedes DI-style construction and synchronous setup/testing.
- Multi-worker-per-process scenarios and Windows are unsupported but not
  documented as such.

**Recommendation**
Document the constraints, and consider making signal registration opt-in or
process-level rather than per-instance.

**Confidence:** HIGH (mechanism), LOW (impact)

### AR-016 — Blocking `task_queue.put` on a bounded queue; busy-poll intake loop

**Severity:** LOW

**Evidence**
- `valkey_async_worker.py:423` (`await self.task_queue.put(...)` with no timeout)
  inside `fetch_tasks`, which `task_queue_manager` (`async_tasks_processor.py:515-528`)
  calls only when `not self.task_queue.full()`, then sleeps `0.01` s.

**Problem**
The fullness check and the blocking `put` are not atomic; if the queue becomes
full between the check and the put (e.g. an external producer), `fetch_tasks`
blocks indefinitely, halting intake. The intake loop also busy-polls at 0.01 s.

**Why it matters**
- Latent deadlock/head-of-line blocking on the intake manager; avoidable CPU
  churn at high poll rates.

**Recommendation**
Use `put_nowait` with a retry/backoff, or a dedicated intake queue, or a
`put` with timeout; consider event-driven intake rather than polling.

**Confidence:** MEDIUM

## Cross-Cutting Analysis

### 1. Worker instances are effectively one-shot (AR-001 + AR-004 + AR-007)

Three independent mechanisms combine to make the documented `STOPPED → RUNNING`
restart path unreliable:
- A failed manager leaves a stale `__manager_tasks` entry and cannot be restarted (AR-001).
- Async logging handlers are closed and recorded as `RUNNING`, so they are never restarted (AR-004).
- Managers run before `initialize()`, so a restart that reaches `initialize()` re-ranks resources (AR-007).

The state machine *advertises* restartability, but the implementation does not
support it. This is the single most important cross-cutting issue: it makes the
"lifecycle" claim of the framework false and forces consumers to treat a worker
as a one-shot process.

### 2. Connection/resource ownership is split across the worker and the external logging handler (AR-006 + AR-009)

Two `GlideClient`s with two teardown owners, plus a `connect()` return value that
does not reflect real connectivity, means "is the transport up?" cannot be
answered from one place. The `task_handler` contract hands handlers the whole
worker, further spreading access to shared state. Resource ownership is not
concentrated where the responsibility lies.

### 3. Delivery semantics are undefined end-to-end (AR-005 + AR-010)

Results are dropped, ack-on-enqueue loses tasks, timeout-requeue can duplicate
them, and the one raising path (empty task type) escapes the error→`TaskResult`
conversion. There is no single owner of "what happens to a task after it is
handed off" — the processor, the watchdog, and the transport each make
independent decisions.

### 4. Responsibility leakage from the processor into handlers and back (AR-008 + AR-009)

The processor exposes its internal queue/trackers by reference, and handlers
receive the full processor. The intended seam (`handle(task_data) -> TaskResult`)
is bypassable in both directions, so the subsystem boundary exists in types but
not in enforced access.

### 5. Extension is via subclassing with implicit ordering (AR-002 + AR-007)

Manager override behavior depends on MRO iteration order that is inverted
relative to documentation, and hook correctness depends on the order of
`_start_managers` vs. `initialize()`. Both are implicit contracts that fail
silently rather than at construction time.

## Architectural Recommendations

### Priority 1 — Should fix first

1. **Fix manager restart and stale-task bookkeeping** (AR-001). Replace the
   in-place stop/start with a fresh-task replacement, add bounded retry/backoff,
   and ensure `__manager_tasks` is always cleaned up. This is a correctness fix
   with no public-API change.
2. **Fix logging lifecycle resumability** (AR-004). Record `STOPPED` on shutdown
   and either re-create handlers on restart or document instances as one-shot and
   align the state machine. Pick the instance-restart policy explicitly.
3. **Fix connection-state symmetry** (AR-006). Make `connect()` set/clear
   `_client` only on verified success, and centralize the two clients' teardown.

These three are cheap, high-leverage, and unblock the rest of the review.

### Priority 2 — Important

4. **Split `BasicAsyncWorker`** (AR-003) into a manager-runtime component and a
   logging-lifecycle component; keep the public API stable.
5. **Correct manager discovery order and decorator semantics** (AR-002) so
   subclass overrides work as documented.
6. **Define the task delivery/ack/retry contract** (AR-005) and add a result sink
   + transport-ack-on-success before building on top of it.
7. **Tighten error boundaries** (AR-010): consume all task exceptions, propagate
   handler-init failures, convert empty-task into an error result.

### Priority 3 — Opportunistic

8. **Config validation** (AR-011): fail loudly, never overwrite user config.
9. **Encapsulate state** (AR-008): read-only views + explicit enqueue/wait APIs.
10. **Unify handler registration** (AR-009): single key concept + explicit
    precedence + narrow handler context.
11. **Timestamps** (AR-012) via `default_factory`.
12. **Cleanup** (AR-013, AR-014): remove `pyaml`/dead constant, consolidate pytest
    config, fix test mocks; document loop/platform constraints (AR-015); guard the
    bounded `put` (AR-016).

## Suggested Target Architecture

The desired direction keeps the layered hierarchy but relocates responsibilities
so each component owns one concern, and makes resource ownership explicit.

```mermaid
flowchart TD
    subgraph Public
        API[scietex.service __init__]
    end

    subgraph Core
        W[BasicAsyncWorker] --> MR[ManagerRuntime]
        W --> LL[LoggingLifecycle]
        W --> SM[ServiceStateMachine]
        P[AsyncTaskProcessor] --> W
        P --> Q[TaskQueue + ResultSink]
        P --> HR[HandlerRegistry]
    end

    subgraph Contract
        H[TaskHandler ABC] --> S[schemas]
        H -. context, not full worker .-> P
    end

    subgraph Valkey optional
        VW[ValkeyWorker] --> P
        VW --> Transport[Single ConnectionOwner]
        VW --> VConfig[valkey_config schema]
    end

    MR --> T[Manager tasks]
    LL --> LH[Async logging handlers]
    Transport --> Glide[GlideClient]
    LH -. shared transport .-> Transport

    API --> W
    API -. guarded .-> VW

    classDef core fill:#eef;
    classDef opt fill:#efe;
    class Valkey optional opt;
```

Key changes vs. today:

- **`ManagerRuntime`** owns discovery/start/stop/restart of managers, with
  correct MRO order, bounded retry, and clean bookkeeping. `BasicAsyncWorker`
  orchestrates state and delegates.
- **`LoggingLifecycle`** owns async-handler start/stop and honors a clear
  restartability policy.
- **`TaskQueue + ResultSink`** centralize enqueue and result/ack handling; the
  processor no longer hands out its internal queue/trackers by reference.
- **`HandlerRegistry`** unifies registration and dispatch with explicit
  precedence; handlers receive a narrow context, not the full worker.
- **Single connection owner** in the Valkey layer (or an explicit pool) serves
  both task/heartbeat traffic and logging, with one teardown ordering.

## Migration Strategy

Incremental, dependency-ordered, no big-bang rewrite:

1. **Phase 1 — Correctness fixes (no API change).** Fix AR-001 (manager restart),
   AR-004 (logging status/restart), AR-006 (connect symmetry). These are internal
   and unblock everything else. *(Independent; do first.)*

2. **Phase 2 — Extend manager semantics.** Correct discovery order + decorator
   binding (AR-002). Depends on Phase 1's clean restart bookkeeping. Add tests
   for override and failure-restart behavior.

3. **Phase 3 — Define task delivery semantics.** Resolve AR-005 contract (ack/
   result sink/retry) and AR-010 (error boundaries) together, since both concern
   what happens to a task post-dispatch. Depends on Phase 2 only for stable
   manager behavior.

4. **Phase 4 — Extract components.** Split `BasicAsyncWorker` (AR-003) and
   centralize connection ownership (AR-006 follow-up). Depends on Phases 1–3 to
   have a stable behavioral baseline to refactor against.

5. **Phase 5 — Tighten boundaries.** Encapsulate state (AR-008), unify handler
   registration (AR-009), config validation (AR-011). Depends on Phase 4 for the
   internal seams to attach to.

6. **Phase 6 — Hygiene.** Timestamps (AR-012), dead code/config (AR-013), test
   fixes (AR-014), platform documentation (AR-015), bounded `put` (AR-016).

## Open Questions

1. **Are worker instances intended to be restartable?** The state machine says
   yes; the implementation says no. This decision gates AR-004 and part of the
   target architecture.
2. **What is the delivery guarantee target?** Exactly-once, at-least-once, or
   best-effort? This determines the ack/result-sink and dedup design for AR-005.
3. **Is a single shared `GlideClient` acceptable to the external
   `scietex.logging` package?** AR-006's cleanest fix depends on the external
   handler's ownership contract, which lives outside this repo.
4. **Is `pyaml` required transitively by `scietex.logging`?** Could not be
   confirmed from this repo; affects AR-013.
5. **Are multiple workers per process a real requirement?** Affects signal
   ownership (AR-015) and whether the framework should drop the
   single-worker-per-loop assumption.
6. **Is the control/PubSub path (`listening=True`) a planned feature?** It is
   currently dead code in `valkey_config.py`; unclear whether to keep, finish, or
   remove.
