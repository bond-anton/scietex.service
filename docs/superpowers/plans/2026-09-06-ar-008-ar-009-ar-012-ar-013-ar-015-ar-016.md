### Task 5: AR-015 — Move signal registration out of `__init__` into `start()`

**Files:**
- Modify: `src/scietex/service/basic_async_worker.py:196` (remove call from `__init__`)
- Modify: `src/scietex/service/basic_async_worker.py:496-506` (`_setup_signal_handlers` — make loop-safe + Windows-safe)

- Modify: `src/scietex/service/basic_async_worker.py:703-743` (`stop()` — deregister on full stop)

**Interfaces:**
- Consumes: nothing.
- Produces: workers constructible outside a running loop; signal handlers registered only while running; no-op on Windows.

**Context (verified):**
- `__init__` calls `self._setup_signal_handlers()` at `basic_async_worker.py:196`.
- `_setup_signal_handlers` (`:496-506`) calls `asyncio.get_running_loop()` (raises if no running loop) and `loop.add_signal_handler(SIGINT/SIGTERM, ...)` (Unix-only; `NotImplementedError` on Windows).
- The handler callback does `asyncio.create_task(self.exit(), name="StopTask")` → `exit()` sets `exit_requested` and calls `stop()` → graceful `_shutdown()`.
- `start()` (`:633-658`) spawns `asyncio.create_task(self._startup(), name="Start")` when state is STOPPING/STOPPED. `start()` is always called from within a running loop (all tests/examples call `await worker.start()` inside `asyncio.run`/pytest-asyncio).

- No test or example exercises signals directly (`grep SIGINT/SIGTERM/signal` in `*.py` returns only source/docstring mentions, no test usage). So moving registration is safe for the suite.
- `_shutdown()` (`:660-701`) sets state STOPPED at the end; `stop()` is the natural deregistration point.

**Design:** Register in `start()` (guarded to run only when actually spawning a startup, i.e. the STOPPING/STOPPED branch), deregister in `stop()` when the worker reaches STOPPED. Guard `_setup_signal_handlers` with `hasattr(loop, "add_signal_handler")` so Windows construction/start is a no-op rather than raising. Add a `_remove_signal_handlers()` helper mirroring registration.

- [ ] **Step 2: Make `_setup_signal_handlers` loop-safe and Windows-safe**

Replace the body of `_setup_signal_handlers` (`:496-506`) with:

```python
def _setup_signal_handlers(self) -> None:
    """
    Set up signal handlers for graceful shutdown.

    Registers handlers for SIGINT and SIGTERM signals that will
    trigger a graceful shutdown of the worker. No-op on platforms
    without ``loop.add_signal_handler`` (e.g. Windows).
    """
    loop = asyncio.get_running_loop()
    if not hasattr(loop, "add_signal_handler"):
        return
    for sig in (signal.SIGINT, signal.SIGTERM):
        loop.add_signal_handler(sig, lambda: asyncio.create_task(self.exit(), name="StopTask"))
    self.logger.log(logging.DEBUG, "Signal handlers are all setup")


def _remove_signal_handlers(self) -> None:
    """Remove the SIGINT/SIGTERM handlers registered by ``_setup_signal_handlers``."""
    loop = asyncio.get_running_loop()
    if not hasattr(loop, "remove_signal_handler"):
        return
    for sig in (signal.SIGINT, signal.SIGTERM):
        loop.remove_signal_handler(sig)
```

### Task 6: AR-016 — Remove unbounded-block risk on bounded-queue `put`

**Files:**
- Modify: `src/scietex/service/valkey/valkey_async_worker.py:460` (`_recover_pending_tasks`)
- Modify: `src/scietex/service/valkey/valkey_async_worker.py:510` (`fetch_tasks`)
- Modify: `src/scietex/service/async_tasks_processor.py:589-602` (`task_queue_manager` — optional backoff tightening)

**Interfaces:**
- Consumes: nothing.
- Produces: intake never blocks indefinitely on a full bounded queue; a full queue is treated as "try again next poll" rather than a hang.

**Context (verified):**
- `self.__task_queue` is `asyncio.Queue(maxsize=self.queue_size)` (`async_tasks_processor.py:118`), bounded (default `DEFAULT_MAX_TASKS_QUEUE_SIZE = 2`).
- `task_queue_manager` (`:589-602`) checks `if not self.task_queue.full(): await self.fetch_tasks()` then sleeps `task_queue_manager_sleep_time` (default 0.01s). The check-then-put is not atomic.
- `ValkeyWorker.fetch_tasks` (`:470-518`) and `_recover_pending_tasks` (`:424-468`) both `await self.task_queue.put(...)` with no timeout. If the queue fills between the `full()` check and the `put`, intake blocks forever, halting the TaskQueueManager.
- Drain side: `task_manager` (`:570-578`) consumes via `asyncio.wait_for(self.task_queue.get(), timeout=TASK_QUEUE_FETCH_TIMEOUT)` and calls `task_done()` in `handle_task`'s finally (`:552`).
- The Valkey intake reads at most one entry per `fetch_tasks` call (`count=1`), and `_recover_pending_tasks` loops over claimed entries.

**Design:** Replace the blocking `await self.task_queue.put(...)` with a non-blocking `put_nowait` wrapped in a try/except `asyncio.QueueFull`. On a full queue, drop the item back to the transport (leave the stream entry pending / do not record the entry id) so the next poll retries it — preserving at-least-once semantics without blocking. This is the minimal, behavior-preserving mitigation; it does not change throughput semantics (the manager already polls at 0.01s).

- [ ] **Step 1: Make `fetch_tasks` put non-blocking**

In `src/scietex/service/valkey/valkey_async_worker.py`, replace the put at `:510`:

```python
                                task_data = msgspec.msgpack.decode(payload_bytes, type=TaskData)
                                await self.task_queue.put((UUID(task_id), task_data))
                                self._task_entry_ids[UUID(task_id)] = entry_id
```

with:

```python
                                task_data = msgspec.msgpack.decode(payload_bytes, type=TaskData)
                                try:
                                    self.task_queue.put_nowait((UUID(task_id), task_data))
                                except asyncio.QueueFull:
                                    # Queue is full; leave the stream entry pending
                                    # (do not record its id) so the next poll
                                    # redelivers it. Never block the intake manager.
                                    self.logger.log(
                                        logging.DEBUG,
                                        "Task queue full; deferring task %s",
                                        task_id,
                                    )
                                    continue
                                self._task_entry_ids[UUID(task_id)] = entry_id
```

> Note: `asyncio` is not currently imported in `valkey_async_worker.py`. Add `import asyncio` at the top of the file (after the `import logging` at line 10).

- [ ] **Step 2: Make `_recover_pending_tasks` put non-blocking**

In `src/scietex/service/valkey/valkey_async_worker.py`, replace the put at `:460`:

```python

                            await self.task_queue.put((UUID(task_id), task_data))

Returning early on a full queue is safe: `_recovered` is already True (set before the call at `:489-491`), so the remaining pending entries are not re-claimed this run but stay pending in the stream and are redelivered on the next worker start (at-least-once preserved).

### Task 7: AR-008 — Stop exposing internal mutable state by reference

**Files:**
- Modify: `src/scietex/service/basic_async_worker.py:208-219` (`events` property)
- Modify: `src/scietex/service/async_tasks_processor.py:152-167` (`task_handlers`, `running_tasks` properties)

- Update call sites: `tests/test_async_task_processor.py`, `tests/test_valkey_worker.py`, `examples/async_task_processor.py`

**Interfaces:**
- Consumes: nothing.
- Produces: read-only views for `events`, `task_handlers`, `running_tasks`; a controlled `enqueue_task()` seam for producers; `task_queue` no longer handed out by reference.

**Context (verified) — every external mutation/read site:**
- `events` property (`basic_async_worker.py:208-219`) returns `self.__events`. External uses are **read-only**: `examples/async_service.py:63`, `examples/valkey_async_service.py:31`, `examples/async_task_processor.py:213`, `tests/test_basic_async_service.py:43` all call `.wait()`/`.is_set()`. Internal code (`:696-698,721-723,732-734,752`) mutates `self.events[...]` — must keep working.
- `task_handlers` property (`async_tasks_processor.py:152-162`) returns `self.__task_handlers`. Only internal read: `_find_task_handler` (`:378`). No external mutation.
- `running_tasks` property (`:164-167`) returns `self.__running_tasks`. Only internal reads/mutations (`:454,551,570,617,663`). No external mutation.
- `task_queue` property (`:179-182`) returns `self.__task_queue`. External **mutations**: `tests/test_async_task_processor.py:70,133,189,231,258` (`await proc.task_queue.put(...)`), `tests/test_valkey_worker.py:176,223` (`worker.task_queue.get_nowait()`), `examples/async_task_processor.py:172-174` (`self.task_queue.full()`/`put`). Internal reads/mutations: `async_tasks_processor.py:445-447,552,572,600` and `valkey_async_worker.py:460,510`.

**Design decision (least-disruptive, closes the finding while keeping tests/examples working):**
1. `events`: return a read-only `MappingProxyType` view. Internal code already mutates via `self.events[...]` — that would break. So internal code must switch to mutating `self.__events` directly (private), and the property returns a read-only proxy. This is safe because all external uses are reads.
2. `task_handlers` / `running_tasks`: return `MappingProxyType` views. Internal code already uses `self.__task_handlers`/`self.__running_tasks` for mutation in most places but reads via the property in `_find_task_handler` (`:378`), `cleanup` (`:454`), `task_manager` (`:570`), `watchdog` (`:617`), `handle_task` (`:551`). Reading through a MappingProxyType is fine (iteration, `.items()`, `.pop()` on the proxy would fail — but `:551` and `:663` call `self.running_tasks.pop(...)`). **Those internal `.pop()` calls must switch to `self.__running_tasks.pop(...)`.** Iteration over the proxy is fine.
3. `task_queue`: do NOT hand out the raw queue. Add a public `enqueue_task(task_id, task_data)` method (non-blocking `put_nowait` with `QueueFull` handling) and a `task_queue_empty()`/`task_queue_full()` read helper if needed. Update the internal `valkey_async_worker.py` puts to use `enqueue_task`, and update tests/examples to use `enqueue_task` instead of `task_queue.put`. For the valkey tests that read via `get_nowait`, add a test-only read path or keep a narrow internal accessor.

> **CRITICAL user decision:** `task_queue` is a documented public property (`async_tasks_processor.py:179-182`) and is the documented enqueue mechanism in `fetch_tasks` docstrings (`:580-587`) and `AGENTS.md`. Removing it is a **public API break**. Two options:
> - **(A) Full encapsulation (recommended):** remove the `task_queue` property, add `enqueue_task()`/`dequeue_task()` methods, update all 8 external call sites + internal valkey puts. Cleanest, but breaks any downstream subclass that overrides `fetch_tasks` and does `self.task_queue.put(...)` (e.g. `examples/async_task_processor.py:174`).
> - **(B) Keep property but document as internal:** return the raw queue but mark the property private/deprecated. Does not actually close the finding.
> Recommend (A). This needs explicit user sign-off because it changes the public API surface that `fetch_tasks` subclasses rely on.

- [ ] **Step 1: Make `events` read-only**

In `src/scietex/service/basic_async_worker.py`, change the `events` property (`:208-219`) to return a read-only view:

```python
    @property
    def events(self) -> Mapping[str, asyncio.Event]:
        """Read-only view of lifecycle events for external coordination.

        Contains ``exit_requested`` (set when an exit is requested) and
        ``exit`` (set when the worker has fully stopped). External code
        must only read these events (``wait()``/``is_set()``); mutation is

### Task 8: AR-009 — Unify handler registration and pass a narrow context

**Files:**
- Modify: `src/scietex/service/async_tasks_processor.py:284-298` (`add_task_handler`), `:300-334` (`_start_task_handler`), `:365-381` (`_find_task_handler`), `:355-363` (`remove_task_handler`), `:425-428` (`initialize`)
- Modify: `src/scietex/service/task_handler/basic.py:24-35` (`TaskHandler.__init__`)
- Update call sites: `tests/test_async_task_processor.py`, `tests/test_task_handler_basic.py`, `examples/async_task_processor.py`

**Interfaces:**
- Consumes: nothing.
- Produces: single registration key concept (task-type based); explicit dispatch; handlers receive a narrow context object instead of the full worker.

**Context (verified):**
- `add_task_handler(handler_name, handler_class)` (`:284-298`) stores `handler_name → class` in `__task_handlers_map`. The name is used only for start/stop/remove/logging.
- `_find_task_handler(task)` (`:365-381`) iterates `self.task_handlers.items()` and returns the first whose `handler.supports(task)` is True — **ignoring the registration key entirely**.
- `_start_task_handler(handler_name)` (`:300-334`) does `handler_class(handler_name, self)` — passing the full worker.
- `TaskHandler.__init__(self, name, worker)` (`basic.py:24-35`) stores `self.worker = worker` (typed `BasicAsyncWorker`).
- Handler subclasses use `self.worker.logger` and `self.logger` (which is `self.worker.logger`). Grep of `self.worker.` across handlers: `examples/async_task_processor.py:65,77,81` use `self.worker.logger.info(...)`. `self.logger` is set in `__init__` from `self.worker.logger`.
- Registration call sites: `examples/async_task_processor.py:204-209` (6 calls, some same class under multiple names: `DataProcessingHandler` under `process_data`+`validate_data`, `ImageProcessingHandler` under 3 names), `tests/test_async_task_processor.py:51,63,125,166,184,226`, `tests/test_task_handler_basic.py:49` (direct `DummyHandler("dummy", worker)` construction).
- `supported_tasks` is the real dispatch key: `DummyHandler.supported_tasks=["dummy"]`, `SlowHandler=["slow"]`, `ExplodingSupportsHandler=["exploding"]`, `FailingStartHandler=["failing"]`, `StubbornHandler=["stubborn"]`, `DataProcessingHandler=["process_data","validate_data"]`, `ReportGenerationHandler=["generate_report"]`, `ImageProcessingHandler=["resize_image","compress_image","convert_image"]`.

**Design decision (minimal, closes the finding):**
The registration name and `supported_tasks` overlap. The cleanest minimal unification that preserves all current behavior: **derive the registration key from the handler class's `supported_tasks`** rather than requiring a separate name. Change `add_task_handler` to accept the handler class and register it under every task type in `supported_tasks` (or, if a name is still desired for logging, keep the name but make dispatch precedence explicit).

Two sub-problems:
1. **Name/type duality:** The registration name is redundant with `supported_tasks`. Minimal fix: keep `add_task_handler(handler_name, handler_class)` signature (public API) but make dispatch precedence explicit and consistent. Since `_find_task_handler` already dispatches purely on `supports()`, the registration name is only a lifecycle handle. The real issue is that one class can be registered under multiple names AND one task type can match multiple handlers with implicit "first wins" precedence.
2. **Full-worker coupling:** Pass a narrow context instead of `self`. Handlers only need `logger` (and, in examples, `self.worker.logger` which is the same object). A minimal narrow context is an object exposing `logger` (and optionally `service_name`/`worker_id`). But handlers currently store `self.worker` and examples call `self.worker.logger` — changing to a context object requires updating those references.

> **CRITICAL user decision:** This is the deepest finding. Two viable scopes:
> - **(A) Narrow-context only (recommended, lower risk):** Keep `add_task_handler(name, class)` and the name-based lifecycle, but change `TaskHandler.__init__` to receive a narrow `context` object (exposing `logger`, `service_name`, `worker_id`) instead of the full worker. Update the 3 example `self.worker.logger` references to `self.logger` (already available) and the `DummyWorker` in `test_task_handler_basic.py`. This closes the coupling half of AR-009 without touching the registration API.
> - **(B) Full unification:** Also change registration to be type-derived (register by `supported_tasks`, drop the name param or make it optional), and make dispatch precedence explicit (error on ambiguity). Larger blast radius: changes `add_task_handler` signature and every call site, plus the `_start_task_handler`/`remove_task_handler`/`initialize` name-keyed logic.
> Recommend (A) for this pass, with (B) as optional future work. Confirm scope with the user.
